# 异体字规范化的**人工补丁**——只放"上游数据确实没有、或者上游给错"的字。
#
# 这份文件存在的理由必须写清楚:HanVariants.txt 本体是 scripts/gen-han-variants.py 从
# **上游数据**(Unicode Unihan + OpenCC 词库)推出来的,不是手工列的字表 —— 那种"撞见一个
# 字才补一个字"的被动积累正是 collector 里 toSimplified 的注释批评过的做法。但实测下来有
# 一小类字上游真的不认识、或者上游给的关系明显不对,只能人工兜一下,每一行都要给出理由。
#
# 格式:变体字<TAB>大陆规范字<TAB>理由      (目标写 `-` 表示**否决**:永不折叠这个字)
# 空行和 # 开头的行忽略。补充条目最后合入(来源标记 override),否决条目直接从产物里剔除。

# ── 补:上游完全没有可用关系的字 ──────────────────────────────────────────
# 祂:20 世纪基督教中文文献造的字(对神的第三人称)。Unihan 里 U+7942 只有 kUnihanCore2020
# 一个字段,**没有任何 k*Variant 关系**(2026-09-03 逐字段核过),OpenCC 三张表里也没有。
# 本机歌词库实测 50 次 / 2 首。
祂	他	Unihan 无任何变体关系(现代造字);本机语料 50 次/2 首

# 痲:Unihan 只把它关联到「痳」(U+75F3),而「痳」本身也不是大陆通用字 —— 顺着上游关系走会
# 折到另一个同样没人用的字上,推不出「麻」。大陆规范里 痲疹/痲痹 一律写「麻」。
# 本机语料实测 1 次 / 1 首。
痲	麻	上游只关联到同样非通用的「痳」,推不出「麻」;本机语料 1 次/1 首

# (「痺」不在这里:它的 kSemanticVariant 指向「痹」(U+75F9,在 G 集里),生成器自己就能推出
#  痺→痹,不需要补。2026-08-22 那版手工表里有它,是因为当时还没有这条推导链。)

# ── 否决:上游关系明显不适用于中文歌词 ────────────────────────────────────
# 卍:Unihan 把它跟「万」列为 kSemanticVariant(U+534D → U+4E07),但它在中文语境里是**佛教
# 符号**、不是「万」的异体写法;歌词里出现「卍」几乎一定是符号用法,折成「万」就是改写。
卍	-	Unihan 关系成立但语境不成立:它是佛教符号,不是「万」的异体

# 雝:Unihan 给的 kSemanticVariant 是 {廱, 簌, U+2AA9D},其中只有「簌」在 G 集里,于是推导
# 会得出「雝→簌」——**明显错的**,「雝」是「雍」的异体(而 Unihan 没有记这条关系)。
# 这一条是"上游数据不全导致唯一候选选错"的样本,留着当例子。
雝	-	上游唯一的通用候选「簌」是错的(它是「雍」的异体,而上游没记这条)
