# LyrimuseがLast.fmにScrobbleするしくみ

*[English](scrobbling.md) · [简体中文](scrobbling.zh-CN.md) · **日本語** · [한국어](scrobbling.ko.md) · [Español](scrobbling.es.md) · [Français](scrobbling.fr.md) · [Deutsch](scrobbling.de.md) · [Italiano](scrobbling.it.md) · [Português (Brasil)](scrobbling.pt-BR.md) · [Tiếng Việt](scrobbling.vi.md) · [Русский](scrobbling.ru.md)*

## 1. 再生がカウントされる条件

次の条件が**すべて**そろったときに、再生が送信されます。

| ルール | 値 |
|---|---|
| 十分な時間再生した | 曲の半分（上限240秒）。曲の長さが不明な場合は240秒。Last.fmに限り、より厳しいタイミングも選べます（§1b参照） |
| 曲が十分に長い | `≥ 30s`（長さが不明な曲は通します）。オフにできます（§1a参照） |
| 広告ではない | Spotifyの広告枠を検出してスキップします |

再生状態は5秒ごとに取得し、経過時間は実時間で積み上げます。そのため、一時停止中はカウントが止まり、シークしても水増しされません。2回の取得の間隔が60秒を超えた場合（Macがスリープした、エンジンが再起動したなど）、その空白は加算せずに捨てます。

これらのしきい値は[Last.fmのScrobbleガイドライン](https://www.last.fm/api/scrobbling)に合わせています。

### 1a. 30秒未満の曲

設定 → 連携サービス → Last.fm → *ルール* → **30秒未満の曲をScrobble**（`scrobble_short_tracks`、デフォルトは**オフ**）。Last.fmのルール *"The track must be longer than 30 seconds"*（曲は30秒より長くなければならない）はクライアント側のルールです。サーバは短い曲を拒否せず、「短すぎる」という無視コードもありません。それでも主要なScrobbleクライアントはどれもこのルールを守っているため、Lyrimuseもデフォルトでは従います。オンにすると、短い曲も「半分再生」のルールを満たした時点でカウントされます（20秒の曲なら10秒）。これは**Last.fm専用**の設定です。短い曲はLast.fmにScrobbleされ（Last.fmの後から送信に使うローカルログにも記録されます）、ListenBrainzには一切送信されません。ListenBrainz側の動作はどちらの設定でも変わりません。

### 1b. Scrobbleのタイミング

設定 → 連携サービス → Last.fm → *ルール* → **Scrobbleのタイミング**（`lastfm_scrobble_point`、デフォルトは**50%**）。曲をどこまで再生したらLast.fmにScrobbleするかを決めます。

| 設定 | 値 | Scrobbleされるタイミング |
|---|---|---|
| **50%**（デフォルト） | `50` | 上記のLast.fmのルール：曲の半分（上限4分） |
| 75% / 90% | `75` / `90` | 曲の長さの75% / 90%を再生したとき。再生した時間だけで判定し、4分の上限はありません |
| 曲の終わり | `end` | 曲を最後まで再生したとき。先送りした分はカウントしません |

Last.fmのルールが下限なので、50%より低い設定はありません。これは**Last.fm専用**です。ListenBrainzとWebプッシュは引き続き50%の時点で送信し、選んだタイミングまで待つのはLast.fmへのScrobble（とLast.fmの後から送信に使うローカルログ）だけです。タイミングより前にスキップした曲はLast.fmに何も送りません。これは設定どおりの動作で、Scrobbleが失われたわけではありません。長さが不明な曲はデフォルトのルールに従います。

*曲の終わり*は、曲が切り替わった時点で最後に観測した再生位置から判定します。終わりから12秒以内（短い曲は長さの10%以内）なら最後まで再生したとみなすので、プレーヤーのクロスフェードやギャップレス再生の切り替えでScrobbleが止められることはありません。

## 2. 送信する内容

`track.scrobble` は履歴に恒久的な記録を書き込みます。`track.updateNowPlaying` は「再生中」の表示を設定するだけで、何も保存しません。

| フィールド | `track.scrobble` | `track.updateNowPlaying` |
|---|---|---|
| `artist` | ✅ | ✅ |
| `track` | ✅ | ✅ |
| `timestamp` | ✅ | — |
| `album` | 空でない場合 | 空でない場合 |
| `duration` | 判明している場合 | 判明している場合 |

これ以外の情報はLast.fmに届きません。Last.fmのAPIはScrobbleで `mbid`、`albumArtist`、`trackNumber`、`chosenByUser`、`streamId`、`context` も受け付けますが、Lyrimuseはどれも送信しません。

## 3. 書き換えないもの

ListenBrainzへの送信、およびLast.fmの*すべて*モードと*最初のみ*モードでは、アーティスト名、曲名、アルバム名をプレーヤーが報告したとおりに送信します（Last.fmの*スマート*モードは、カタログの項目に合わせてアーティストと曲名を書き換えます。次の節を参照してください）。

唯一行う処理は、目に見えない文字の整理です。ノーブレークスペースと全角スペースは通常のスペースに、ゼロ幅文字とBOMは削除、連続する空白は1つにまとめ、先頭と末尾の空白は取り除きます。これをしないと、目に見えないノーブレークスペース1つでLast.fm上に別のアーティストができてしまいます。

目に見える部分は何も変えません。大文字・小文字、繁体字と簡体字、かっこ内のサブタイトル、複数アーティストの表記もそのままです。`PRINCE` は `PRINCE` のまま、`無所謂` は `無所謂` のまま、`一口 (The Day You Left Me)` はサブタイトルを残します。

デフォルトで外部の照会によって名前を「正規化」しない理由：

- Lyrimuseはかつて、まさにそれをしていました。実際の約2,500曲のライブラリを監査したところ、書き換えられたアーティスト名がおよそ200件見つかり、その中には `USA for Africa` → `Xtc Planet` や `LBI利比` → `Safehse` もありました。Last.fmの公開アーティストページにいったん書き込まれたScrobbleは、後から修正できません。修正データベースが凍結されているためです。
- Last.fmのScrobbleガイドには、*"Do not use the corrections returned by the now playing service as input for the scrobble request, unless they have been explicitly approved by the user."*（ユーザが明示的に承認しない限り、Now Playingサービスが返した修正をScrobbleリクエストの入力に使わないこと）と2回書かれています。また、その `autocorrect` フラグは[レガシーと明記されています](https://support.last.fm/t/scrobbles-of-japanese-artists-getting-separated-by-romanization-of-their-name/119906)。
- 調査したオープンソースのScrobbleクライアント9つ（Web Scrobbler、Pano Scrobbler、Navidrome、Maloja、rescrobbled、mpdscribble、mpdas、Koito、multi-scrobbler）のうち、デフォルトで外部の照会からアーティスト名を書き換えるものは1つもありません。

## 4. マッチングモード

設定 → 連携サービス → Last.fm → *ルール* → **マッチングモード**（`~/Library/Application Support/me.yudaotor.lyrimuse/lyrimuse-features.json` の `lastfm_match_mode`）：

| モード | 値 | 効果 |
|---|---|---|
| **スマート**（新規インストール時のデフォルト） | `smart` | Last.fmのカタログからこの曲の項目を探し、その項目のアーティストと曲名を送信します（下記参照） |
| カスタム | `custom` | 変更してよい部分を選びます（下記参照） |
| **そのまま**（既存インストールでのデフォルト） | `raw` | プレーヤーの報告どおり。ネットワーク通信はしません |

*カスタム*を選ぶと、曲名とアーティストの2行が表示されます。

| 行 | 選択肢 | 効果 |
|---|---|---|
| **曲名** | 一致する項目 | 曲名をカタログの項目の表記に置き換え、アルバム名から「 - Single」「 - EP」を外します（`lastfm_match_track`） |
| | そのまま | 曲名を報告どおりに送ります |
| **アーティスト** | 一致する項目 | アーティストをカタログの項目の表記に置き換えます（`lastfm_match_artist`） |
| | 最初のみ | 共演の表記を最初のアーティストだけに切り詰めます（`Khalil Fong & Fiona Sit` → `Khalil Fong`）。純粋な文字列処理で、ネットワーク通信はしません（`lastfm_match_first_artist_only`） |
| | そのまま | アーティストを報告どおりに送ります |

2行のうち片方だけ「一致する項目」にした場合、**もう一方のフィールドがすでに一致している候補だけを採用します**。そうしないと、カタログに存在しない組み合わせになり、リスナーが1人（あなた）だけの幽霊項目に戻ってしまいます。

「最初のみ」は「一致する項目」と違い、**何もマッチしなかったときにだけ**適用されます。マッチした表記はすでにLast.fmが認識している項目であり、それを切り詰めると存在しない項目になってしまうからです。たとえば `Hall & Oates / Maneater`（リスナー80万人）は `Hall` になってしまいます。そのため曲名「そのまま」・アーティスト「最初のみ」は、旧来の*最初のみ*モードとバイト単位で同じで、ネットワーク通信もしません。

`lyrimuse-features.json` がすでにある環境では*そのまま*がデフォルトのままです。共演の表記を切り詰めるのは取り消せない操作で、履歴からFiona Sitが消えてしまうからです。Navidromeの同名のオプション（`Lastfm.ScrobbleFirstArtistOnly`）もデフォルトはオフです。

分割は控えめに行います。`/` は `,` や `&` とは別に扱うので、`K/DA` や `AC/DC` が `K` や `AC` に分割されることはありません。

### スマートモード

プレーヤーが報告する文字列と、Last.fmのカタログが同じ録音に付けている名前は、文字が一致しないことがよくあります。そのまま送信すると、再生は「幽霊」項目に記録されます。MBIDもアルバムもなく、長さはゼロ、リスナーは1人（あなた）だけです。David Taoの《那个女孩》で実測した例：プレーヤーは `陶喆, 卢广仲 / 那个女孩` と報告しますが、Last.fmにはこの項目がまったくありません。簡体字の `陶喆 / 那个女孩` はリスナー126人。この曲の本当の項目は繁体字の **`陶喆 / 那個女孩` で、リスナー889人、再生回数4,580回、カタログ上の長さもあります**。Last.fm自身の `autocorrect` は役に立ちません。繁体字と簡体字の間の対応付けをしないためです。

そこで*スマート*は、送信前に曲を照会します。

1. 報告どおりの内容で `track.getInfo` を呼びます。**MBIDがあれば**、以後一切手を加えません。MBIDはカタログ上の実在の項目であることを示す最も強いシグナルで、正しく表記された共演（Hall & Oates）が「リスナーが多い」という理由でソロのページに移されるのを防ぎます。
2. MBIDがなければ、**ちょうど3か所**から候補を集めます。報告どおりの内容、表記上の最初のアーティスト、そしてそのアーティストの項目のうち、曲名を正規化すると同じキーになるもの（`artist.getTopTracks`。もともとリスナー数の順に並んでいます）です。
3. 候補のうちLast.fmが実際にカタログに載せているもの（MBIDがある、リスナーが500人以上、カタログ上の長さがある、のいずれか。幽霊項目には3つとも欠けています）の中から、最もリスナーの多いものを選びます。長さを検証したうえで、そのアーティストと曲名を送信します。判定は一度だけで、以後ずっと維持します。条件を満たす候補がなければ報告どおりに送信し、90日後に再確認します。

`track.search` はあえて**使いません**。文字列をそのまま検索するので、繁体字の項目は見つからず、`张泽熙 / 那个女孩` のような同名別曲のヒットも除外できないからです。曲名の正規化で吸収するのは、同じ録音の表記ゆれだけです。繁体字と簡体字、異体字、ダイアクリティカルマーク、フィーチャリング表記（`(feat. X)`）、再発盤のタグ（`(Remastered 2014)`、`(Bonus Track)`）が該当します。**Live、Remix、アコースティック、インストゥルメンタルの表記は常に残します**。これらは別の録音だからです。選ばれた候補は長さのチェックにも通る必要があります（双方に長さがあり、8秒を超えて違う場合は却下します）。

実際の240曲で測定した結果：33曲を書き換え、162曲をそのまま送信、45曲は判定不能でした。例：

| 報告された内容 | 送信した内容 | リスナー数 |
|---|---|---|
| `周杰倫 / 手写的从前` | `周杰倫 / 手寫的從前` | 100 → 4,515 |
| `Wang Leehom / 奇遇的起点` | `王力宏 / 奇遇的起點` | 1 → 144 |
| `SZA & Phoebe Bridgers / Ghost in the Machine` | `SZA / Ghost in the Machine (feat. Phoebe Bridgers)` | 175 → 856,376 |
| `PRINCE / Walk Don't Walk (2023 Remaster)` | `Prince / Walk Don't Walk` | 231 → 16,178 |

照会が失敗した場合（ネットワーク、レート制限、不正な応答、曲リストに到達できないなど）は、報告どおりのタグを送信し、何もキャッシュしません。一時的な不具合が恒久的な判定になることはありません。判定は、その根拠となった証拠とともに `~/Library/Application Support/me.yudaotor.lyrimuse/lyrimuse-lastfm-catalog.json` に保存されます。このファイルを削除すると、すべて判定し直します。

旧来のキーは引き続き読み込みますが、書き込みはしません。動作を変えずに移行します。`lastfm_scrobble_artist_mode` の `smart` → スマート、`all` → そのまま、`first` → 曲名「そのまま」・アーティスト「最初のみ」のカスタム。さらに古い真偽値 `lastfm_scrobble_first_artist_only=true` は `first` と同じ扱いです。

## 5. Scrobbleが失敗した場合

正しい対応が異なるため、失敗は分類して扱います。以下の「記録する」とは、再生をローカルログに書き込むことです。ログの内容は、最近の再生の下にある「未送信N件」の隣の「後から送信」ボタンで手動で始める**後から送信**で、あとから送信できます。

| 起きたこと | Lyrimuseの対応 |
|---|---|
| リクエストがMacから出ていないことが確実（DNS、接続の失敗） | 記録する。後から送信で送信できます |
| 確実に保存されていないとわかる理由でサーバが拒否した（認証情報の誤り、レート制限） | 記録する。後から送信で送信できます |
| 送信したが結果が不明（タイムアウト、接続の切断、判別できないサーバエラー） | 記録するが、後から送信で自動的に再試行することは**決してありません** |
| サーバが曲を受け取ったうえで、内容そのものを拒否した | 記録しない。サーバが返した実際の理由を表示します |

3行目があるのは、タイムアウトの場合、Last.fmが再生を保存していて受領通知だけが失われた可能性があるからです。再試行すると、手作業で削除しなければならない重複ができてしまうため、結果が判別できない失敗は自動では再試行しません。

後から送信でさかのぼれるのは**13日**までです。一度送信を試みた再生を、リアルタイムの経路が再び送信することはありません。再生はリクエストが成功した*後*ではなく、送信する*前*に試行済みとしてマークされるため、リクエストの途中でクラッシュしても二重送信は起きません。

## 6. 統合が行われる場所

Last.fmにはプレーヤーが報告した内容が届きます。そのため、同じ人物を `Khalil Fong` と `方大同` の両方で報告するライブラリでは、Last.fm上に2人のアーティストが表示されます。

Lyrimuseの中では、再生回数、ランキング、「N回目の再生」の数字でこれらを統合します。繁体字と簡体字の正規化、ローマ字表記の名前の別名、カタログ上のノイズの除去（`(Remastered 2014)`、`(feat. …)`、`(Explicit)`）、アーティストごとの別名表を使います。送信前ではなくローカルで統合するのは、ローカルでの誤った統合は再読み込みで元に戻せる一方、誤ったScrobbleは公開ページへの恒久的な編集になるからです。

## 7. よくある質問

**ScrobbleなしでLyrimuseを使えますか？**
はい、それがデフォルトです。設定 → 連携サービスでLast.fmアカウントに接続するまで、何もScrobbleされません。歌詞とアートワークの取得はこれとは別で、アカウントの接続有無にかかわらず、アーティスト名と曲名を公開の歌詞プロバイダ（Netease、QQ、Kugou、LRCLIB、Musixmatch、AMLL）に送信します。これらのソースは設定で絞り込んだり、無効にしたりできます。

**Last.fmのプロフィールに同じアーティストが2回表示されるのはなぜですか？**
プレーヤーが2つの異なる名前を報告し、両方とも報告どおりに送信されたためです。Lyrimuseは自身の統計の中ではこれらを統合しますが、Last.fm上で統合するにはLast.fm側でScrobbleを編集する必要があります。

**送信前に名前を整えることはできますか？**
できません。それが必要な場合、現実的なのは自動の照会ではなく、ユーザが編集できるルール表の形です。[Maloja](https://github.com/krateng/maloja)のやり方を参考にしてください。

**iPhoneでの再生はどうなりますか？**
LyrimuseがそれらをLast.fmに送信することはありません。Apple自身のScrobbleの仕組みでLast.fmに届きます。Lyrimuseはそれを読み戻し、Macでの再生と並べて統計に表示します。

**名前を書き換えずに、Last.fm上でアーティストを統合できますか？**
APIではできません。Last.fmの `mbid` パラメータが識別するのは*曲*であってアーティストではないため、両方の名前をそのまま残しつつ「この2つの名前は同じ人物」と伝えるフィールドはありません。

**ローカルの再生ログはScrobbleと重複しませんか？**
重複しません。再生を記録するのは、Last.fmアカウントが接続されていないとき、または送信が失敗したときだけです。Last.fmに接続していて正常に動作していれば、ログは空のままです。
