# 05. 灵动岛歌词
> 最后核对:2026-09-09 · 基线:f30bca2+工作树

## 定位

贴在屏幕顶部刘海位置的歌词卡("灵动岛"形态),是与桌面悬浮歌词(经典悬浮窗)平行、完全独立的第二套悬浮歌词实现:独立的 NSPanel、独立的窗口控制器、独立的开关,两种形态可同时开启互不排斥。稳态常显"播放指示条 + 歌名 + 播放控制 + 当前歌词逐字高亮 + 封面小图",hover 时向下多展开一块"下一句预览 + 迷你进度条"。

## 入口与展示面

- **设置页 → 歌词显示 →「灵动岛」分段**(2026-08-31 起是**编辑台**版式,见下面「编辑台改造」):内容区顶上一块 `NotchEditorStage` —— 一小片屏幕顶端(仿菜单栏条 + 物理刘海 + 桌面壁纸),灵动岛卡片 **1:1** 挂在上边缘(展开宽放不进舞台时整组等比缩小,见「宽度 → 展开态可以更宽」末条),渲染的是与真窗口**同一份** `NotchLyricsView`(通过 `NotchChromeSource` 协议换了个不建窗口的替身 chrome),hover 展开真实可用(2026-09-06 起卡片本身**不接**播放键等控件的点击,取而代之的是几块**可点区域**:点左耳 / 右耳 / 歌词行 / 展开态内容,直接在被点的区域旁弹出管这块内容的浮层,见「编辑台改造 → 预览卡上的可点区域」)。编辑台顶上是**两行**工具栏,共七个浮层入口(第一行「风格」「屏幕」「左耳」「右耳」,第二行 2026-09-01 加的「歌词行」「行为」「展开态」,按钮上都带当前值摘要),舞台内部卡片正下方一根**双滑块**宽度调整条(左 = 稳态宽、右 = 展开宽,2026-09-06 起,见「宽度 → 展开态可以更宽」)。编辑台**下面**才是总开关卡(「灵动岛歌词——紧凑地贴着屏幕顶部的刘海显示」)。设置不跟开关联动:灵动岛关着也能先配好。分段顶部**不再有钉住的预览条**(那一层收不到点击事件)。
- **菜单栏状态项 →「快速开关」子菜单 →「显示灵动岛歌词」**。
- **首次引导页(OnboardingView)** 也有同一个开关。
- **窗口本体**:`NotchLyricsWindow`(NSPanel),无边框、level 为 `.screenSaver`(高过系统菜单栏,否则贴不进刘海那一条)、跨所有 Space、全屏应用之上可见、外观固定 `.darkAqua`、`hasShadow = false`、不可被用户移动。位置永远是算出来的(贴死屏幕顶边、水平对齐刘海中心),没有"锁定位置"概念,也不持久化位置。
- 没有专属全局快捷键;全局快捷键里跟它有关的只有"歌词时间轴微调"(其反馈横幅显示在灵动岛上,见下)。

## 行为规格

### 「显示歌词」开关(2026-08-31)

`AppSettings.notchShowLyrics`(默认开)。用户原话:「多一种形态,对于有一些想要显示播放状态的但是又不想有歌词挡住视线的人可以用;就是只保留屏幕菜单栏那部分高度,歌词部分不显示」。⚠️ **入口挪过三次,均系 2026-08-31~09-01 这两天**:最初就在「风格」浮层的最后一行,08-31 用户要求"拿出来单独放,不要合并到风格里面"而搬到编辑台下面一张独立的「行为」卡片;09-01 那张卡片(连同后来并入的显示封面/展开态四项)先被改成"点开才配置"的浮层形态、落进「行为」浮层;同一天晚些时候用户又要求"放到歌词行选项里面去配置"——它管的是歌词行本身渲不渲染,跟「歌词行」浮层里的「显示封面」是同一类东西,归那边更贴切,现在的入口是工具栏**「歌词行」浮层**(`NotchLyricRowPopover`),不在「风格」浮层、也不在「行为」浮层里。

关掉之后:歌词行连同它那 44pt **一起不渲染**,卡片只剩顶行那一条(= 刘海/菜单栏的高度),灵动岛退化成一条贴着屏幕上沿的**状态栏** —— 宽度照旧(两只耳朵的模块照常显示),但不占菜单栏以下的任何一个像素。**hover 展开仍然可用**:那是够到播放控制和进度条的唯一入口,而关歌词的人要的正是"只显示播放状态";只是展开区里那行「下一句歌词预览」跟着一起不画(它是歌词)。

⚠️ **判据走 `NotchChromeSource.showsLyrics`,不许在视图里直接读 AppSettings**:卡片高度(`NotchWindowRoot`)、内容渲染(`NotchLyricsView`)、设置页编辑台三处要用同一个值,而后两者拿到的是替身 chrome;`NotchWindowRoot` 只观察 controller、不观察 AppSettings(2026-08-19 性能审计定的纪律,别为一个开关把整卡挂回去观察全部设置)。真窗口那一侧由控制器订阅设置后 `@Published` 出来,预览那一侧现读即可。

⚠️ 同一天把**卡片高度公式收成了唯一一份**(`NotchChromeSource` 的协议扩展 `cardHeight`),`NotchWindowRoot` 和 `NotchEditorStage` 都读它。在此之前两处各写一遍,而入参已经从 1 个(收起)涨到 4 个(收起 / 有没有曲目 / 展不展开 / 显不显示歌词)—— 本章设计决策里那条「两处各自判断必然漂,漂的表现是行不见了高度还留着」说的就是这种地方。展开区那行下一句预览的"留不留高度 / 画不画"同理收成一个 `showsExpandedLyricPreview`。

### 三种形态:收起 / 稳态 / 展开

窗口本身**常驻最大尺寸**(**展开宽** × 展开态高,2026-09-06 之前展开宽 ≡ 稳态宽),形态切换是卡片在这个固定透明窗口里自己变大变小(`NotchWindowRoot`),窗口 frame 只在屏幕几何或宽度设置变化时才动。窗口比稳态卡片宽出来的那两截跟下方多出来的高度一样是纯透明区,点击穿透到底下的菜单栏(实测见 `NotchWindowRoot` 文件头)。

- **收起**(`isCollapsed`,计算属性 `(!isPlayingNow || isAdBreakNow) && !isExpanded`,2026-08-19 加入广告维度):卡片收**高度**——只留顶行那一条(高度 = 刘海高/菜单栏高),歌词行和展开区连同内容整块淡出+向上轻缩(anchor 在顶部,跟卡片同一条弹簧,不是硬切);**宽度缩到 `min(稳态宽, 刘海宽 + 2 × 34 + 20)`**(`NotchWindowRoot.cardWidth` 的收起分支,2026-08-19 三键搬进展开卡后耳朵只剩封面/音浪,见「顶行」节的 `collapsedRow`)。
  - ⚠️ 代码里多处旧注释(`NotchLyricsWindowController` 文件头、`NotchChromeSource.isCollapsed` 的 doc)仍写着"收起缩到刘海本身大小/兜底胶囊 120pt",这是 2026-08-16 窗口重构前的旧行为(本节此前也写过一版"收起宽度不变、恒为 steadyCardWidth",2026-09-06 按代码订正)。控制器里的 `collapsedCardWidth` 属性仍在计算和发布,但当前工作树**没有任何消费方**(死状态)。
  - 收起态 hover 上去仍能重新展开出完整内容(含播放按钮,可用来恢复播放)——2026-08-17 把 `isCollapsed` 从"只在 recomputeGeometry 里赋值的存储属性"改成计算属性,修的就是"暂停时鼠标移上去没反应"。
  - **Spotify 广告插播也收起**(2026-08-19 用户拍板"和暂停一样缩回去"):广告期间歌名位显示「广告中」而不是广告物料名(`NotchLyricsView.topRow` 的 displayTitle,MarqueeText id 用显示串以便切进/切出广告时重置跑马灯),歌词行随收起不渲染;hover 仍可展开(控制按钮可切歌跳过广告)。`isAdBreakNow` 由 `$isCurrentTrackAdBreak` 的 sink 写入,同 `isPlayingNow` 的 willSet 坑同一修法:只取 sink 参数值。
- **稳态**(播放中、没 hover):顶行 + 歌词行(44pt,`NotchMetrics.compactRowHeight`)。
- **展开**(hover):在下面再长出 40pt(`NotchMetrics.expandedExtraHeight`):下一句歌词预览(有才显示)+ 迷你进度条 + 时间行。**宽度也可以一起撑开**(2026-09-06):卡片从稳态宽长到展开宽(`NotchWindowRoot.cardWidth` 的 `isExpanded` 分支读 `expandedCardWidth`),两只耳朵和歌词行跟着变宽(`NotchLyricsView` 按 `proxy.size.width` 反推耳宽,视图层不用改);默认两宽相等、不撑开。宽度变化跟高度同一条弹簧。**没有曲目时**(2026-09-07,决策 #31)展开只长出一块 49pt 的「空闲面板」(`idleExpandedPanel`:「没有在播放」+ 提示句 + [继续播放/打开 X │ 设置 · 关闭] 三颗键),不留歌词行也不留三键/进度条那块 —— `cardHeight` 的 `!hasTrack` 分支与面板 frame 读同一个 `NotchExpandedMetrics.idlePanelHeight`。**触发**展开的命中区仍是稳态卡片,展开后光标停在多撑出来的两截上仍算在卡片上、维持展开 —— 展开卡片包含稳态卡片,不会"进了又出"抖动。详见「宽度 → 展开态可以更宽」。
  - ⚠️ **命中区不能只靠 `contentShape`**(2026-09-07 真实 bug,用户报「鼠标还没移到灵动岛上、只是移到它下面,它就已经展开了」)。真机探针实测(在 `NotchWindowRoot.updateHover` 打 hover 进入/退出边沿的 local 坐标 + `NSEvent.mouseLocation` + 窗口 frame,四条记录逐条交叉核对、误差 ≤1pt):`.contentShape(Rectangle())` **只管住了横向** —— local 的原点确实是卡片左上角、x 也确实被约束在卡片宽内,但 **y 一路给到 177,而当时稳态卡片只有 77pt 高**(窗口 482×191),于是卡片下方那片压在用户自己窗口上的透明区照样把它捅开。这是同一个现象的第二形态:2026-08-16 就为它把命中判定从 `NotchLyricsView` 自带的 `.onHover` 挪到宿主层并加了 `contentShape`(当时实测「光标停在卡片下方 24pt 的透明处照样展开」),那次的措施只挡住了一半。**现在 `.active` 分支自己拿坐标跟当前卡片矩形比**(`LyrimuseCore.NotchHoverHit.isInside`,纯函数,selftest 用那四条实测坐标当回归样本),跟设置页编辑台那侧(`NotchEditorStage` 一直是 `point.y <= cardHeight`)口径一致。传的是**当前**卡片尺寸,所以展开后那几个点又算在里面,维持展开的语义不变。

- **展开区高度按内容算**（`NotchExpandedMetrics.height(hasLyricPreview:hasScrubber:)`，2026-08-21 用户报「没有歌词的时候这块太大、很多空的地方」）：展开区原来恒高 76pt 且 `alignment: .top`，而三样内容里两样是条件渲染的——下一句歌词预览（没歌词就没有）、迷你进度条（没时长就没有，见 `NotchScrubber` 的两个分支）。两样都缺时里面只剩一排三键，剩下 **41pt 全是底部空白**。现在按段累加：三键+底边距+余量 35（恒有）／预览行 17／进度条 24 → 三样齐仍是 **76，跟改动前逐字相等**（有歌词有时长时布局一点没动），只有预览 52，只有进度条 59，都没有 35。⚠️ 两个入参刻意是**曲目级**信号（这首歌有没有歌词／有没有时长），不是“此刻有没有下一句”——后者会让最后一句唱完时卡片突然矮 17pt、下一首又长回来，肉眼是抽动；代价是“有歌词但此刻恰好没下一句”时那 17pt 是空的，稳定压倒紧凑。**窗口和设置页预览容器仍用 `maxHeight`**：窗口恒按最大形态开（卡片在里面变大变小），跟着内容缩会让后面换到有歌词的歌时卡片被窗口边界硬裁。卡片高度（`NotchWindowRoot.cardHeight`）和展开区自己的定高**走同一个函数、同一组入参**，两处各自判断必然漂，而漂的表现是底部多一条空隙或最下面那排三键被裁掉。

形态切换动画(`NotchWindowRoot.cardAnimation`)分四条弹簧:收起 0.45s 临界阻尼(不回弹);hover 展开 `interactiveSpring(0.38, 0.8)`(跟手);**hover 移开 `spring(0.38, 0.9)`**(2026-09-06 起单独一档,不下探 —— 此前落在下面那条 0.42/0.8 上,SCK 逐帧探针实测每次收回都先缩到稳态以下 2px 再爬回来、尾巴 150～200ms 亚像素蠕动,详见决策 #25;`.animation(_:value:)` 用变化后的新状态求值,区分这一档靠 `NotchWindowRoot.wasExpanded`——onChange 在 body 之后回写的上一帧 isExpanded);其余(开始播放弹出等)`spring(0.42, 0.8)`。系统开了"减弱动态效果"(reduceMotion)时全部直接跳变。**出场动画（2026-09-03，见 §显示/隐藏 与决策 #19）**：卡片「从无到有」露面时由 `NotchWindowRoot` 的 keyframeAnimator 播一遍「从刘海撑开」——`NotchRevealShape` 裁剪区从真刘海宽 / 顶行高起，横向 0.20s 撑到全宽，纵向按住 0.06s 后 0.24s 长到全高，内容 0.10s 后 0.16s 淡入，总 0.30s（`NotchReveal`，LyrimuseCore）；只裁剪不缩放，reduceMotion 不播。

### 播放状态与收起时机

收缩判定订阅的是 `PlaybackCoordinator.$isPlayingSmoothed`——对"停"有 0.25 秒宽限(`stopGracePeriod`,2026-08-17 从 2s 压到 0.5s,2026-09-02 再压到 0.25s),吸收换歌间隙/seek 的瞬时 false,避免灵动岛缩回去又弹出来;"起"不延后,恢复播放立刻响应。暂停 ≈0.25s 后卡片收起(歌词行卷回顶行)。

### 顶行(收起态唯一保留的部分)

`NotchLyricsView.topRow`,左右两只耳朵各 `(卡片宽 − notchWidth − 20) / 2`,中间给物理刘海让出 `notchWidth` 宽的空当(物理刘海是硬件不发光区域,横向落进去的内容会被真实挡掉;无刘海屏幕 notchWidth = 0,顶行整条可用)。空当里唯一的内容是**品牌胶囊彩蛋**(`notchSeam`,2026-09-03;**2026-09-06 起它不画在顶行的 HStack 里,而是钉在 body 的 ZStack 顶部居中**,顶行两个版本只用 `notchGap` 留出同宽空当,理由见决策 #18 末尾):圆体「Lyrimuse」胶囊,底色跟灵动岛当前主色走(`playback.accent`,同歌名/音浪),上半截淡白渐变 + 0.5pt 浅描边作光泽,字色按 WCAG 相对亮度(> 0.179 取黑)选黑/白;高 min(22, 顶行高−8) 夹到 ≥14,肉眼永远看不到、只在截全屏/录屏/投屏/镜像到无刘海显示器时露出;只在 `notchWidth > 0`(排除无刘海屏与外接屏镜像副本)且 `hasTrack`(空闲黑块时不挂牌子,会议共享不暴露)时画;「截屏/录屏时隐藏」开着时整窗不进截图。见设计决策 #18。两只耳朵**朝刘海那一侧**各内缩 `NotchMetrics.earNotchInset = 6`(2026-08-20 用户要求「歌手不要那么紧贴真实刘海」):三段严丝合缝铺满时右耳的左边界正好压在刘海右沿,装不下的歌手名(跑马灯从左起)第一个字就贴着黑边 —— 实测改前 0.5pt、改后 7.0pt(截图逐列对比度测量,`VALORANT/Grabbitz/bbno$`)。⚠️ 内缩必须写在 `.frame(width: earWidth)` **之前**,写在之后等于把耳朵整体变宽 6pt,三段不再铺满、背景形状与刘海空当会错位:

- **两种形态,同一个视图**(2026-09-06 起 `topRow` 一个 HStack 按 `isCollapsed` 换耳朵里的**内容**,不再是 `collapsedRow` / `topRow` 两个视图整行互换,理由见决策 #18 末尾):收起态 = 左耳专辑封面小图(`earArtwork`,点它打开歌词窗口,没封面就留空、不画占位方块)、右耳播放指示条,跟 iPhone 灵动岛收起形态同构;稳态/展开 = 左耳、右耳各一个**可配模块** + 播放指示条。两种形态下左耳内容贴左外缘、右耳贴右外缘、朝刘海侧同样内缩 6pt(收起态 34pt 耳朵减 6 剩 28,放得下 23pt 封面 / 14pt 音浪);用户本来就配"左封面、右音浪"时两种形态的视图身份完全相同,收放只是内容跟着耳朵边沿平移,连淡入淡出都没有。**压根没有曲目**(`!controller.hasTrack`,不管收起没收起)时另有一档(2026-09-07,决策 #30):左耳不看配置、固定画 App 图标(`idleAppIcon`,`NotchMetrics.earAppIconSide` ≈ 26pt,不接点击),卡片底色整块盖成纯黑(`body` 里那层 `Color.black` 的 opacity 条件从 `isCollapsed` 扩成 `isCollapsed || isIdleNoTrack`),跟真刘海融成一块;右耳的静止音浪照旧。控制键不在耳朵里(2026-08-19 用户逐步拍板:岛本来就是 hover 展开的,光标到耳朵之前卡片已经展开,完整三键在展开卡的进度条下方,见「hover 展开区」)。
- **耳朵模块可配**(2026-08-31,`NotchEarModule` + `notchLeftEar`/`notchRightEar`,入口是编辑台工具栏上**左右各一个**的「左耳」「右耳」浮层)。八选一:**歌名 / 歌手 / 专辑 / 封面 / 播放控制 / 已播时长 / 剩余时长 / 不显示**,默认 `左=封面 右=不显示`(2026-09-07 起,见「默认值的一次整体校准」;此前是 `左=歌名 右=歌手`,那一版跟可配之前那套写死的排布**逐像素一致**)。
  - **只管稳态/展开这一套耳朵**。收起态那套(左封面右音浪)不可配,理由是硬的:收起态单侧耳宽 `NotchMetrics.collapsedEarWidth = 34pt`,11.5pt 字号下连两个汉字都装不下,文字模块放进去只能是断头;给它单独配一套 = 多两个下拉而可选项只剩图标类,收益配不上复杂度。

  求值间隔 **0.28s → 0.10s**。旧注释「再快就显得毛躁」是**跟随机高度绑在一起**的结论 —— 目标值互不相关时越快抖得越凶;换成连续函数之后,快反而是顺滑的前提(采样越密越贴近那条曲线)。补间曲线 easeInOut → **linear**:目标值本身已在连续曲线上,再套 ease 会在每个采样点两端各加一次加减速,把平滑的正弦啃成一段段顿挫 —— 那是机械感的另一半。

### 唱完就切到下一句(2026-08-23)

单行展示面(灵动岛歌词行 / 菜单栏歌词 / 菜单栏面板那一格)**不再等下一句开始才换行**:本行

`LocalPlaybackSource` → `PlaybackCoordinator`。

- 离下一句还远(长间奏)→ 中段显示 **♪**,到剩 5 秒时才亮出下一句;
- **行级 LRC 不抢跑**:不知道一行唱多久就不猜 —— 猜早了会在人还在唱这句时把它换掉,比原来更糟;
- **最后一句唱完不切走**:后面没有句子可提前,切成 ♪ 只会让尾奏变空屏。

### 风格(四种背景)

`NotchCardStyle`:纯黑 / 磨砂玻璃(`.thickMaterial`,窗口外观锁死 darkAqua,永远深色)/ 深色渐变(左上到右下三段冷色)/ **跟随封面**(默认值)。

⚠️ **这四个选项不只决定背景**(2026-08-31 起):`.coverArt` 同时让**前景**(歌名/歌手/歌词/逐字染色/播放键/进度条/音浪,全卡 16 处 `accentOrWhite`)走封面主色,其余三种前景恒为白。也就是「跟随封面」现在指**整张卡**跟着封面走。改动前前景由 `AppSettings.followsCoverArt` 决定,而那是**桌面悬浮歌词**「配色」组里的开关(两个入口——设置页悬浮歌词段、悬浮窗 ⚙ 快捷菜单——都挂在悬浮歌词上),只开灵动岛的用户根本够不到它;更糟的是它跟这里的「跟随封面」**同名不同义**,去灵动岛这一段找只会找错。合并之后灵动岛不多一个开关,也不再受悬浮歌词那边任何设置影响,撞名问题一并消失。

"跟随封面"(`NotchLyricsView.backgroundLayer`):铺 PlaybackCoordinator **预烘焙**的模糊图 `blurredArtworkImage`(2026-08-19 性能审计落地 —— 原来视图层挂 `.blur(radius: 20)` 活滤镜,窗口播放期间因逐字填色/音浪/跑马灯几乎永动,GPU 每次重合成都重算同一个模糊;现在封面到货时用 CIGaussianBlur 离线烘一次,源 = highResArtworkImage ?? artworkImage,降采样到 720px、sigma 40≈原 20pt 半径@2x,clampedToExtent 让边缘实心)。`scaledToFill` + **显式钉回卡片尺寸的 frame** + 压 45% 黑不变;打底层只兜烘焙空窗(几十 ms),2026-09-06 起是一块**纯色**(`#14212A`,渐变的中间档)而不是 darkGradient 那道渐变,也不再套 `NotchHangingShape` —— 它整个压在模糊图底下看不见,却在 hover 展开时随卡片尺寸每帧重画一遍 rgba64 渐变着色,占了动画期间主线程 24% 的忙时(决策 #25);底部圆角统一由外层那一道裁剪负责。同理收起态那层黑罩也是纯 `Color.black`。模糊半径等效 20 而不是歌词窗口的 60:灵动岛画布又矮又宽,60 会把任何封面抹成统一深灰。没有封面数据时整个退回深色渐变。封面切换 0.5s 淡入淡出(触发键:烘焙图实例比较,一条覆盖原来 artworkData 字节比较 + 高清替代实例比较两条)。

卡片轮廓统一是 `NotchHangingShape`:顶部两角直角(贴死屏幕顶边,视觉上"从刘海长出来")、底部两角 20pt 圆角;整个 ZStack 统一 `clipShape` 一次,任何内容不越界。

### 强调色(跟随封面取色)

`NotchLyricsView.accentOrWhite`(实现在 `NotchPlayback.accent`,预组合去重):**风格选中「跟随封面」(`notchCardStyle == .coverArt`)且这首歌真取到了主色(`notchAccentColor`)**时才用封面色,否则一律白色。取不到主色时自动落回白,跟 `.coverArt` 背景在没有封面时退回 darkGradient 是同一种兜底,不需要额外分支。

⚠️ 2026-08-31 之前这里的判据是 `AppSettings.followsCoverArt`(桌面悬浮歌词「配色」组里的开关,跨形态生效;标题原为「文字跟随封面」,2026-08-26 去掉「文字」二字缩短)。它跟「风格」里的「跟随封面」**字面撞名、语义不同**(一个管前景取色、一个管背景铺图),而且入口全在悬浮歌词那一段。两者合并进 `notchCardStyle` 之后:灵动岛与悬浮歌词彻底独立,撞名消失,灵动岛也没有因此多一个开关。

`notchAccentColor` 的算法(`PlaybackCoordinator` 里那条 `Publishers.CombineLatest3`):封面均值色 → `brightenedAccent`(HSB 亮度地板 0.62)→ `accentForDarkBackdrop`(Rec.709 感知亮度地板 0.62,补 HSB 地板拦不住的饱和冷色)。这两步都假设"背景永远接近纯黑"。

⚠️ **coverArt 卡片风格下这条假设不成立,2026-08-27 修**(用户反馈"歌词和背景对比度太低,看不清楚")。「风格」四选一里纯黑/磨砂玻璃/深色渐变三种背景确实恒暗,唯独 coverArt 背景是「模糊封面 + `LocalPlaybackSource.notchCoverArtOverlayOpacity`(0.45)黑叠加」——**亮度正比于封面本身的亮度**,不是恒定的暗。实测坐实(方大同《Run From Your Love》所在专辑《JTW 西游记 (Gold)》的黄底封面,均值 #BBA45E、Rec.709 luma 0.645):均值本来就在两步地板之上,原地板全是无操作,文字色=原始均值色;coverArt 背景 = 均值 × 0.55,luma 只有 0.355(不暗)。文字跟这个背景实测 WCAG 对比度只有 2.78,连大号文字门槛(3.0)都够不到——灵动岛字号(9~13.5pt)按 WCAG 定义也够不上"大号文字"这一档,该按 4.5 的门槛要求。

修法沿用桌面悬浮歌词描边取色同一个哲学(`accentAgainstStroke`):量**真实相邻色**的对比度,不是赌"背景反正很暗"的假设。`LocalPlaybackSource.accentForCoverArtBackground` 直接复用 `accentAgainstStroke`,把"描边色"换成按封面均值算出来的 coverArt 背景估计值(`均值 ×(1 - notchCoverArtOverlayOpacity)`),够不到 4.5 就沿"混白"方向调,已经够对比的原样放行。只在 `notchCardStyle == .coverArt` 时多算这一步——纯黑/深色渐变/磨砂玻璃三种风格背景是真的暗,不需要、也不该多算。⚠️ `NotchLyricsView.backgroundLayer` 渲染背景用的黑叠加不透明度和这里估算背景用的必须是**同一个数**,两处共享 `notchCoverArtOverlayOpacity` 常量,不能各写一份——那正是这次问题被放大的次要原因(即便当初想到要估算背景,数字对不上估算也会白做)。

⚠️ **08-27 这版修复本身还留了一个反方向的洞,2026-08-31 修,且第一版补丁本身还不够、当天改了两次**(用户反馈"封面偏白的时候,歌词颜色很奇怪,全黑,太突兀了")。`accentAgainstStroke` 内部按"跟候选色同一侧(更亮/更暗)优先"选调整方向,但**只要那个方向的解析解跑出 [0,1] 区间就整体判定"这个方向不行",转头去另一侧精确算解**——问题是另一侧的精确解不见得温和:封面很白时,候选文字色已经很亮,往亮的方向调只需要贴到纯白就行,但因为"贴纯白"这个数字本身没有精确打满目标,算法就整体放弃这个方向,转去暗的方向——而对着一个本来就偏亮的背景,往暗的方向要精确打满同一个 minContrast,解出来的目标亮度会逼近纯黑。于是出现"翻方向精确达标,数值上更好,但从『贴近纯白』直接跳到『几乎纯黑』"的观感灾难——这正是"歌词全黑,太突兀"的根因。

修法是加一道"贴边界已经足够接近"的容忍窗:贴边界(纯白/纯黑)的对比度只要①先过 WCAG 大号文字基线 3.0、②达到 minContrast 的一定比例,就直接采用贴边界的结果,不再翻方向凑那最后一点数值差距。两个判据都在 `LocalPlaybackSource.accentAgainstStroke` 里,判据①保证 minContrast 用默认值 3.0 调用时(桌面悬浮歌词描边取色)这条分支数学上永远不会触发(canGoUp 为 false 时贴边界对比度必然 <3.0,过不了判据①,行为原样不变,这条关系不随判据②的比例常数变化),只有像 `accentForCoverArtBackground` 这种传更高 minContrast(4.5)的调用才可能吃到。

⚠️ **判据②的比例常数第一版拍了 95%,当天就被用户下一次真实反馈打脸**:95% 是拿一个手算的假设场景(luma≈0.187)验证过的,而用户实际在播的是方大同《红豆》(Timeless 专辑)——大面积白底 + 一角深色人像,均值色下载真实封面用 CIAreaAverage 算出来是 (0.894,0.895,0.907),coverArt 背景估出来 luma≈0.207,贴纯白只能拿到对比度 4.08,是 minContrast=4.5 的 90.7%,被 95% 的门槛卡在外面,复现的还是同一个"翻成近黑"。教训**跟第九轮背景取色系数那次一模一样:手算/假设的数字算得再仔细,也换不来拿真实素材实测一遍**——把比例常数从 95% 放宽到 80%(《红豆》的 90.7% 和已知反例 mid-gray 的 57% 之间留了足够余量,两头都不贴边界),selftest 补了用《红豆》真实均值色跑通 `accentForCoverArtBackground` 全链路的断言。

`notchAccentColor` 的取色管线(`PlaybackCoordinator` 订阅拼装,只给灵动岛消费):封面均值色(高清优先)→ `LocalPlaybackSource.brightenedAccent`(HSB 亮度地板 0.62,提亮多少按比例压饱和;近黑兜底成中性灰 0.72)→ `LocalPlaybackSource.accentForDarkBackdrop`(**感知亮度地板 0.62**,Rec.709 luma,朝白色线性混合一步到位)。第二道是灵动岛专属:HSB 地板拦不住饱和冷色(纯蓝 brightness 1.0、luma 只有 0.07),贴深色背景区分度差。桌面悬浮歌词用的是另一条 `artworkAccentColor`(判据是跟描边的对比度),两者不通用。

2026-08-16 起强调色覆盖灵动岛**几乎全部**前景:歌名、播放指示条、五种状态占位文字、逐字歌词、下一句预览、进度条(填充和底槽)、时间文字、控制按钮、瞬态横幅——之前只有歌词正文吃它,状态文字会"有歌词跟封面色、变「暂无歌词」突然跳白"。唯一例外是封面小图描边。

### 瞬态横幅(NotchTransientCenter)

一条短暂**盖住歌词行**的提示(图标 + 文字 + 可选进度细条),不改卡片高度、不动顶行,0.18s 淡入淡出,与歌词行同高同排版重量。单例中心做 cancel-rearm:连按多次以最后一次为准(每次 `show` 先取消上一个隐藏任务;`Task.sleep` 被取消后还要再查 `Task.isCancelled`,光 `try?` 挡不住被取消的任务去清空)。默认时长 1.4s。

当前两个生产者:
1. **歌词时间轴微调快捷键**(`GlobalHotkeys`):按一次闪"歌词偏移 +0.50s"(正号显式带出,方向可辨)。只有灵动岛这一种形态有此反馈;只开桌面悬浮歌词的用户按快捷键仍无任何视觉反馈。注意:菜单栏「歌词时间轴」里的等价按钮**不**闪横幅,只有快捷键路径闪。
2. **系统音量/静音变化**(`VolumeMonitor.apply`):显示音量百分比 + 分档 speaker 图标 + 进度条,1.2s。启停**固定跟随灵动岛总开关**(2026-08-17 删掉了独立开关;灵动岛关着提示无处显示,监听也不挂)。⚠️待核对:VolumeMonitor 对输出设备切换/多输出设备场景的监听行为本章未核对(只核对了启停条件与渲染)。

可见性推论(代码结构直接决定):横幅挂在歌词行上,收起态(没在播放且没 hover)歌词行不渲染,横幅不可见;开着「暂停/无播放时隐藏」时窗口整个 orderOut,更看不到。「所有屏幕」模式下横幅在每块屏的灵动岛上同时显示(单例被所有实例的视图观察)。

### 宽度

固定宽度,不随歌词长短变化(超长歌词靠跑马灯,不靠加宽)。**2026-09-06 起宽度是一对**:稳态宽 `notchContentWidth`(默认 252,下限)和展开宽 `notchExpandedContentWidth`(默认 482,上限)——两个默认值 2026-09-07 前同为 360、共用一个常量,见「默认值的一次整体校准」,见下面「展开态可以更宽」;本节下文说的"宽度 / 设定值 / 滑杆下界"若不特别指明,都是**稳态宽**那一份。稳态实际宽度 = `max(设定值, 耳朵下限)`(`contentWidth(baseWidth:notchWidth:leftEar:rightEar:)`)。

**耳朵下限 = `notchWidth + 单只耳朵最小宽 × 2 + 10 × 2`,而"单只耳朵最小宽"跟着左右耳配的是什么模块走**(2026-08-31 第二轮,用户:「目前宽度最小值不应该是 340 吧,我看依旧左右耳占用了很大空间;可以最小值再小一些,支持调到更小」)。在此之前它是一个写死的 `minEarWidth = 70` —— 那是耳朵还写死"左歌名 / 右三个播放键"时按最坏情况定的常量,耳朵改成八选一之后就成了一刀切:两只耳朵都配「不显示」时,下界照样按"放得下三个播放键"算。

每个模块的最小宽(`NotchEarModule.minEarContentWidth(contentTopInset:)`)。**判据是"再窄就真的被裁",不是"再窄就不好看"** —— 往上多给一个 pt 就是替用户把岛的下限抬高一个 pt:

| 模块 | 最小宽 | 依据 |
|---|---|---|
| 不显示 | 0 | — |
| 歌名 / 歌手 / 专辑 | **0** | 跑马灯,窄了只是滚得勤、再窄就是什么都不显示,**不会坏** —— 所以不该参与决定下限。见下面那条⚠️ |
| 封面 | `earArtworkSide` 现算 | 边长 `max(16, contentTopInset − 10)`,**不给估计值**(这台机器菜单栏 32 → **22pt**)。跟两处渲染共用同一个函数,不许各写一份 |
| 已播 / 剩余时长 | 39 | `-12:34`/`-88:88` 在 11.5pt 等宽数字下实测 39.0。⚠️ 时间**不能**靠跑马灯兜底(一秒一跳的数字滚起来读不了)。超 1 小时的曲目(`-1:23:45` = 50.1pt)在最窄处仍会滚,极少数,不为它把所有人的下限抬 11pt |
| 播放控制 | 48 | 三键命中框 15+18+15,`spacing: 0` |

⚠️ **文字那三档给 0 是第三轮改的,别当成漏填**。第二轮给过 24pt(「可读窗口还剩两个汉字」),那是拿"好看"当"会坏"用:它把默认配置(歌名/歌手)的下界钉在 300,而用户看着 300pt 下那两个词旁边的空白说「这里还有很多位置,把最小调整为刚好放得下一个封面,或者刚好放得下一个音浪就好」。给 0 之后下限完全由**真的会被裁的东西**撑着 —— 默认配置就是右耳外缘那簇音浪,正是用户说的"刚好放得下一个音浪"。**代价写在这儿**:拖到最底那一格单耳只有 26pt,右耳的文字被音浪挤成 **0 宽**(左耳还剩 20pt 在滚)。这是滑杆上肉眼可见的连续过程、不是突变,想要文字往回拖两格就有 —— 把这个选择留给用户,而不是替他把区间截掉。

两侧还要各加朝刘海那侧 6pt 的 `earNotchInset`;**挂着音浪的那一只**再加 `EqualizerBars.width`(5×1.8 + 4×1.5 = 15)+ `earWaveSpacing` 5pt —— 除非那只耳朵的模块本身就是播放控制,那时音浪让位。⚠️ **哪只耳朵挂音浪、以及挂不挂,都是可配的**(`notchEqualizerEar` / `notchShowsEqualizer`,2026-08-31 同日加的;在此之前写死右耳,常量也还叫 `rightEarContentSpacing`),所以 `minEarWidth` 里那笔音浪的账是**两只耳朵各自判**(`equalizerAllowance(forEar:module:)`),不是"右耳专属"。⚠️ **两只耳朵恒等宽**(`earWidth = (卡片宽 − 刘海宽 − 20) / 2`),所以取两边需求的**较大者**,不是各算各的;也因此音浪那 20pt 会在卡片宽度上翻倍成 40pt —— **关掉音浪能直接让下界掉 40pt**。

这台机器(刘海实测 **179pt**、菜单栏 32pt)上的实际下界:

| 左耳 / 右耳 | 滑杆下界 |
|---|---|
| **音浪关掉**,且两耳都是文字或「不显示」 | **212** |
| 歌名 / 歌手(2026-09-07 前的默认,音浪在右)、不显示 / 不显示、歌名 / 不显示 | **252** |
| 同上但音浪换到左耳 | 252(对称,不变) |
| 封面 / 任一文字(**封面 / 不显示**同此 = 2026-09-07 起的默认组合) | 256 |
| 任一文字 / 封面 | 296 |
| 任一侧播放控制 | 308 |
| 任一侧时长 | 330 |
| （第一轮之前:任何配置一律） | 340 |

表里"封面在左 256 / 在右 296"这种左右不对称,**来自音浪此刻挂在哪一侧**(默认右),不是左右耳本身有别:同一个「封面」跟音浪不同侧只要 22+6=28pt,同侧要 22+15+5+6=48pt,而两耳等宽,这 20pt 的差在卡片宽度上翻倍成 40pt。把音浪换到左耳,这张表的"左/右"跟着镜像。

⚠️ **几何硬底是 199**(`刘海 179 + 左右各 10`):卡片再窄就整个躲进刘海里了(它水平居中对齐刘海中心)。任何"再小一点"的诉求到这条线为止。

**区间的唯一真源是 `NotchEditorStage.widthRange`(200…800;上界 2026-09-06 从 500 抬到 800,见「展开态可以更宽」末条)**,菜单栏快捷面板那根滑杆也指它(2026-08-31 起)。下界同日从 260 降到 200 —— 耳朵下限跟配置走之后,两只耳朵都「不显示」时能掉到 251,存储层卡在 260 就白让 9pt(刘海更窄的机器让得更多);200 这个数是从上面那条几何硬底 199 来的。两个入口的步长不同:编辑台调整条 step 2(紧挨着实时变宽的卡片,10pt 一格看得出来在跳),快捷面板 step 10(兜底通路、旁边没有预览,粗一点好落值)。落盘值因此可能不是 10 的倍数,那根 10pt 的滑杆照样显示得出来——step 只约束滑杆自己产生的值,不约束模型。

**滑杆能拖的下界 = 这台机器**当前配置下**的耳朵下限**(`NotchEditorStage.usableWidthRange(notchWidth:)`,2026-08-31 用户要求「既然最小就是 339,那么就应该把宽度条最小调整为 339」)。在此之前下界恒为 260,而 260…339 这一段拖了卡片纹丝不动——抬上来之后那截死区不存在了,滑杆每一格都真的会动。

⚠️ **下界是屏幕 _和_ 耳朵配置两者的函数,不是常量**:没有真刘海的屏 `notchWidth == 0`、耳朵下限只剩一百出头,`max` 之后是存储层的 200。⚠️ **改耳朵配置必须重算几何** —— 承担这件事的是 `NotchLyricsWindowController` 里的 `leftEarObserver` / `rightEarObserver`(2026-08-31 补;耳朵刚做成可配那一轮漏了这两条,当时下限还是常量所以看不出来,下限跟着配置走之后漏了就是"选了播放控制、三个键被裁掉半个,直到下次拖宽度才恢复")。两条 sink 都把**参数值**显式传下去,不让下游回读 `AppSettings` —— `@Published` 是 willSet 时机派发,此刻回读拿到的是旧值。⚠️ **存储层的 `widthRange`(200…500)不随屏幕/配置变**——它是"这个值合不合法"的判据,而合法性不该随插了哪块屏、耳朵配成什么而变(宽度是要跟配置一起迁移的,不像 `notchScreenID` 那种机器本地键);低于当前下界的旧值不会被改写,只是渲染时被 `contentWidth` 顶上去,换回窄的耳朵配置那个值原样回来。三条护栏:下界向上取整到 `widthStep` 的倍数(否则"先夹后量化"可能把值量化到下界以下)、下界不许越过上界(留至少一个 step,防 Slider 拿到零长区间)、`snap` 夹的是 usable 而不是存储层区间。

**两个宽度入口的读数一律报「带耳朵的真实宽度」,不报设定值**(2026-08-31 用户要求「这里的宽度帮我改为带上耳朵的宽度,这样就没有歧义了」):编辑台调整条走 `cardWidth`,菜单栏快捷面板走 `NotchEditorStage.effectiveWidth(baseWidth:)`(同一条公式,刘海宽度现读屏幕的 static 版本)。此前编辑台报设定值、再由 caption 补一句「已被两侧耳朵撑到 NNNpt」——同一件事两个数字,还得配一句话解释它们的关系;现在数字跟眼前那张卡逐像素对得上,那句 caption 也删了。代价是拖进下限区间时数字不动,而这正是**正确**的反馈:卡片也没动,两边一致地在说"到底了"。

设置页/快捷面板改完显式调 `applyContentWidthSetting()` 立刻生效(2026-09-06 起三个入口统一经 `NotchEditorStage.commitWidths`,见下);编辑台**拖动中只改本地 `@State`(`draggingSteady` / `draggingExpanded`)、松手才落盘**,理由同悬浮歌词编辑台:每格都写 `@Published` + UserDefaults + 全量几何重算,而编辑台里跑的是真 `NotchLyricsView`,一帧塞不下。

#### 展开态可以更宽(2026-09-06)

用户原话:「把展开状态变为可以更宽,也就是配置宽度的时候可以设置一个上限和一个下限,下限就是正常状态的宽度,上限就是悬浮展开时候的宽度」。

- **模型**:两个键。`notchContentWidth`(稳态宽,下限,老用户一直在调的那个)+ 新增 `notchExpandedContentWidth`(展开宽,上限)。两者**唯一**的不变量是**展开 ≥ 稳态** —— hover 是"多给你看一点",不该反过来把卡片挤窄。算术全部在 `NotchWidthBounds`(LyrimuseCore,selftest 钉着):
  - 读侧(真窗口 `recomputeGeometry` 与编辑台 `expandedCardWidth`):展开真实宽 = `max(稳态真实宽, 展开设定)`。稳态已过耳朵下限,展开不必再算一遍。
  - 写侧(`NotchEditorStage.commitWidths(steady:expanded:)`,三个入口**唯一**落盘路径):落盘前 `normalized` 成 `展开 = max(稳态, 展开)` —— 单滑块入口把稳态拖过展开,展开被顶上去;展开拖到稳态以下,停在稳态。**先写展开、后写稳态**(两个 `@Published` 各派发一次,镜像管理器 combineLatest 在第一次派发时另一个值还是旧的,先抬展开就不制造一帧"展开 < 稳态"的落盘状态);相等守卫与 `notchOverlayEnabled` 守卫都在这一处,调用点不再各写一份。
  - 默认值:2026-09-07 起是**两个**常量 —— `AppSettings.defaultNotchContentWidth = 252` 与 `defaultNotchExpandedContentWidth = 482`(用户把自己在用的这一对定为默认,见「默认值的一次整体校准」)。此前两键**共用**前一个常量(同为 360),理由是"一份常量,防止分开写漏改一个"、以及新装机器上 hover 不会莫名多长一截;拆开之后那份担心由两行紧挨着 + 下面这张对照写法兜住。⚠️ 没变的是另一半:展开键**没存过**时落的是**默认常量**、**不是**用户当前的稳态值 —— 否则老用户的展开宽会被钉在升级那一刻的稳态上,以后调稳态还得再调一遍这个。老用户把稳态调到过 420、展开键没存过的话,`max(420, 482) = 482`。
  - 「重置」不碰它(跟稳态宽同一个取舍:结构性尺寸设置)。selftest「重置覆盖闸」为此把 `defaultNotchContentWidth` 列进豁免名单(该名单此前为空,豁免理由写在名单旁)。
- **窗口**:常驻**展开宽** × 展开态高(`NSSize(width: expandedCardWidth, …)`),稳态卡片居中挂在里面,两侧各 `(展开宽 − 稳态宽) / 2` 的透明区。实测(2026-09-06,稳态 360 / 展开 460):check-windows 报窗口 460×208、中心不变;截窗像素采样顶行不透明列 100…819 px(2x)= 360.0pt,左右透明边各 50.0pt。副本(`NotchMirrorManager`)订阅两个键,任一变都 `syncAll`。
- **卡片**:`NotchWindowRoot.cardWidth` 三分支 —— 收起 `min(稳态, 刘海+88)` / 展开 `expandedCardWidth` / 稳态 `steadyCardWidth`;`NotchLyricsView` 不感知这件事(耳宽从 `proxy.size.width` 反推)。
- **编辑台**:舞台里那根调整条从单 `Slider` 换成**双滑块** `RangeSlider`(`UI/RangeSlider.swift`,自绘;SwiftUI 没有原生双滑块,两根单滑块叠着放会把"同一根轨道的两个端点 = 一个区间"这层意思丢掉)。两只滑块共用 `usableWidthRange`(下界 = 耳朵下限),量化 `SteppedSlider.snap` step 2、不画刻度。交互规则是纯函数 `NotchWidthRangeDrag`(Core,selftest):①按下离哪只近拖哪只,两只重叠时看第一段位移方向(往右 = 上限、往左 = 下限,没动先不认领);②被拖的那只**不越过**另一只 —— 停在对面的值上、不推着走(推走会让"调上限"顺手改掉用户早就调好的稳态宽)。点在轨道空处 = 把较近那只拖过来(同原生 Slider)。**拖哪只滑块,卡片就按哪种形态画**:按住展开那只时 `chrome.setExpandedFromPreview(true)`(卡片变宽也变高,就是 hover 时的样子),松手复原;不这么做拖上限时鼠标在滑杆上、卡片没被 hover,那只滑块改的宽度在画布上看不见。读数「360pt」(两宽相等)/「360–460pt」(`%@–%@pt`),报**真实**宽(经下限与 `max`),不报设定值 —— 口径同 2026-08-31。VoiceOver:两只滑块各是一个可调节元素(`灵动岛宽度` / `灵动岛展开宽度`,一次增减 5 × step = 10pt),读数文本对无障碍隐藏,免得同一个值读两遍。
- **两个兜底入口**各多一根「展开宽度」单滑块(step 10):「全部设置」抽屉 `expandedWidthRow`、菜单栏快捷面板 `.notch` 段。区间 `usableExpandedWidthRange(steadyWidth:)`:下界 = 稳态**真实**宽(向上取整到 step、不越过 `500 − step`,稳态拉满时不给 Slider 零长区间),上界 500;读数 `effectiveExpandedWidth(steadyBase:expandedBase:)`。稳态那根「宽度」的写回也改走 `commitWidths(steady:)`,拖过展开时展开跟着上去。
- **区间上限 500 → 800**(同日稍后,用户拖到 500 后:「最宽还是有点小了,帮我再调大一些」)。两只滑块同一个 `widthRange`,稳态也因此能到 800(没有理由替用户把稳态钉在 500);800 ≈ 14 吋 MBP 逻辑宽 1512 的一半,两侧菜单栏各还剩三百多 pt。代价在编辑台:舞台最宽 600、最窄约 499,卡片超过舞台宽从"差零点几 pt 的角落"变成可达的常态。**处理是整组等比缩小到刚好放下**(`NotchEditorStage.previewScale`):缩放比 = `min(1, 舞台宽 / 展开真实宽)`,**按展开宽算、不按此刻的卡片宽**(否则 hover 一进一出整块屏幕忽大忽小;钉在展开宽上,稳态和展开态同一把尺子、展开时恰好撑满舞台);缩的是「屏幕顶端」整组 —— 仿菜单栏条 + 卡片 + 刘海一起 `scaleEffect(anchor: .top)`,只缩卡片会让刘海空当和菜单栏高度对不上;壁纸不缩;命中测试跟着几何效果变换,缩过的卡片只在画出来的那块上响应 hover。缩了就在舞台底下 caption 写「预览已缩小至 NN%」,免得把缩过的尺寸当真;放得下时仍是 1:1、caption 空。⚠️ 这是当天的**第二版**:第一版照搬悬浮歌词编辑台的"居中裁切 + 两端渐隐带 + 「两端已裁切」"(hover 命中容器还收窄到舞台宽防止舞台外的页面空白触发展开),用户看过后否掉 ——「太大之后,预览放不下」,他要的是看全、不是知道被裁了。悬浮歌词那边溢出是常态(上限 1400 vs 舞台 600)且用户没提过,两边处理方式因此不同,不是漏改。
- **未验证的一点(2026-09-06 写入时)**:hover 撑宽的实机效果没有截到图 —— 截窗只能拍稳态,让卡片展开需要移动指针,而本仓禁止脚本驱动界面做验证;这条路径的判据只有 `NotchWindowRoot.cardWidth` 那一句分支 + Core 的 selftest。以用户目验为准。

### 显示在哪块屏幕

设置项是一个三合一下拉:**自动**(空串)/ **所有屏幕** / 指定某块屏。指定屏幕存的是显示器硬件 UUID(`ScreenIdentity`,`CGDisplayCreateUUIDFromDisplayID`——localizedName 同型号重名、NSScreenNumber 跨会话会变、数组下标随插拔顺序变,都不能用)。

- **自动**:`targetScreen()` = 有真刘海的那块(`safeAreaInsets.top > 0`)→ 再没有退 `NSScreen.main`。不能直接常驻 NSScreen.main——它跟着键盘焦点跳,曾导致灵动岛停在用户看不见的外接屏上(2026-08-07 修)。
- **指定屏拔掉/合盖**:自动回落"自动"逻辑;设置页「屏幕」浮层补一行「已断开的屏幕」(2026-08-31 前是 Picker 的占位 tag —— 选中值在选项里找不到对应 tag 时整个控件会显示成空白,像设置丢了;换成单选列表之后同一个问题的同一条修法);偏好保留,屏插回来即恢复。
- **所有屏幕**(`notchAllScreens`,默认关):`NotchMirrorManager` 给主实例之外的每块屏各建一个钉死(`pinnedScreenID`)的副本控制器。主实例照旧走 `targetScreen()`;主实例占的屏不建副本(否则两个灵动岛严丝合缝叠着,hover 只有上面那个响应)。副本与主实例是同一个类、同一份视图、同一套订阅,唯一区别就是钉屏字段。副本没有自己的设置入口,`notchHideWhenNotPlaying`/`notchHideDuringScreenCapture`/`notchContentWidth` 变化时管理器挨个调 `syncStateFromSettings(…)` 同步 —— **sink 的参数值必须显式传下去**(2026-08-19 修:@Published 在 willSet 时机派发,下游回读存储属性是旧值,原实现镜像宽度恒滞后一档、隐藏开关同步到翻转前的状态),各写入点判等、`orderFrontRegardless`/`setFrame` 只在真变化时执行;`teardown()` 末尾必须 `contentView = nil; hostingView = nil` 破掉 controller↔rootView 保留环(否则每次拔屏/关开关整套窗口+SwiftUI 树永久泄漏);副本不注册自己的屏幕参数观察者(主实例才注册,副本统一由管理器的通知驱动,避免一次插拔跑两遍全量几何);`notchCardStyle`/`followsCoverArt` 等纯渲染项经每个实例各自的 `NotchPlayback` 窄代理订阅(2026-08-19 起视图不再整对象观察 PlaybackCoordinator/AppSettings —— 36 个 @Published 实读约 17 个、47 个设置只读 2 个,无关高频写入原来会打醒整卡 body×镜像数;代理只转发实读字段并 removeDuplicates,accent 由「跟随封面」开关×动态主色预组合去重),仍然天然全实例生效。屏幕插拔时重算副本集合;被钉的屏拔掉时副本不自己挪窗(由管理器销毁),`resolvedScreen()` 返回 nil 直接不动。
- **刘海几何**(`geometry(for:)`):有真刘海时用 `auxiliaryTopLeftArea/auxiliaryTopRightArea` 算出刘海真实宽度和中心点(不假设刘海精确居中);无刘海屏幕退到"假刘海":高度 = 这块屏**当前菜单栏高度**(顶边差 `frame.maxY - visibleFrame.maxY`,下限 24pt 只在菜单栏自动隐藏时兜底;不能用 frame 高度差,那把 Dock 也算进去了),notchWidth = 0,水平居中于整块屏。

### 显示/隐藏

- `setVisible(_:)` 是开/关的**唯一入口**(设置页 Toggle、菜单栏开关、引导页三处都走它),真值持久化在 `AppSettings.notchOverlayEnabled`;打开时顺手把两个隐藏偏好应用上。
- **暂停/无播放时隐藏**(`notchHideWhenNotPlaying`,⚠️ **2026-09-01 起不再与桌面悬浮歌词共用**;入口 2026-09-02 又从"这一段自己的「自动隐藏」卡"并进了编辑台工具栏的「行为」浮层与「全部设置」抽屉「行为」组,行本体是与悬浮歌词共用的 `UI/AutoHideSettingsRows.swift`):开着时暂停**整卡从当前大小直接缩进刘海(scale→0 + 透明,`isVanished`,0.2s ease-in)、再整窗 `orderOut`**(2026-09-02 起;此前是暂停即 orderOut、看不到动画,当时定为"设置语义不是 bug",已推翻;同日中间版"先播收起弹簧再走"被用户目验否掉——不经过暂停收起态,`isCollapsed` 在这个开关开着时不再把暂停算进去):控制器等 `NotchWindowRoot.vanishSettleDelay`(0.25s)后三重校验——代数没被作废、开关与灵动岛仍开、平滑播放态仍是"没在放"——才 orderOut;这半秒里恢复播放则挂着的隐藏作废、卡片直接重新展开,不再有 orderOut→orderFront 两次事务。恢复播放时先 `orderFront` 再翻回 `isVanished=false`。⚠️ **回场:2026-09-03 上午改成瞬时,同日下午又换成「从刘海撑开」出场动画(见本条末尾与决策 #19)**(上午改瞬时时,此前是"从刘海里以 0.42/0.8 弹簧弹出",用户报「从广告变成歌的时候灵动岛的封面是平移过来的,不是直接就切换了外观」)。抓帧坐实(按窗口 ID 连拍那扇窗、24 帧/次):空档期卡片整个消失(连续 13 帧字节数完全相同),新歌开始只跨 1 帧就到终态,中间那一帧卡片明显比终态窄、内容整体偏移——正是 `scaleEffect(0.001 → 1, anchor: .top)` 的中间态;`.coverArt` 风格下卡片背景就是封面模糊图,整卡放大时封面跟着被重新缩放裁切,观感即"封面平移过来"。⚠️ **退场那一档不动**,它是 2026-09-02 用户点过头的;两个方向不必对称——退场是"东西要走了",给动画是交代,回场是"新歌来了",用户要的是立刻看到新外观。两种情况仍立刻隐藏:系统减弱动态效果、用户手动关掉灵动岛。截屏/录屏隐藏走 `sharingType`,不经此路径。见设计决策 #17。**同日下午回场改成「从刘海撑开」出场动画（用户拍板，见决策 #19）**：上午改瞬时是因为缩放路线让封面跟着被重新裁切；新动画只裁剪不缩放（`NotchRevealShape` + keyframeAnimator，控制器 `revealGeneration` 触发，冷启动 / 手动打开灵动岛 / 从刘海回场三种「从无到有」各播一次），封面一个像素都不动，那条反馈的根因不会复现；scale 那一档仍瞬时回 1（渐显交给裁剪）；退场 0.2s 缩进刘海不变。
- **截屏/录屏时隐藏**(`notchHideDuringScreenCapture`,同样已拆开、同一个入口):`window.sharingType = .none`,截图/录屏/会议共享拍不到,本人仍看得见。
- 显示用 `orderFrontRegardless()`(App 是 `.accessory` 策略从不激活成前台,`orderFront(nil)` 会看"是否活跃 App"这个前提)。
- App 启动恢复:`AppDelegate` 只在 `notchOverlayEnabled == true` 的分支里碰 `.shared` 应用隐藏偏好,**不再调 `setVisible(true)`**(历史 bug:会把用户上次关掉的状态覆盖回开)。

### 默认值的一次整体校准(2026-09-07,用户把自己在用的这一版定为默认)

用户原话:"再帮我把目前我灵动岛的设置也设置为默认的"(同一天先后对菜单栏、悬浮歌词做过同样的事,
见 06 章 / 04 章的同名小节)。把他机器上这一段的全部键跟代码默认值逐个比过,动了十项:

| 设置项 | 默认值出处 | 原默认 | 新默认 |
|---|---|---|---|
| 左耳 / 右耳 | `defaultNotchLeftEar` / `defaultNotchRightEar` | 歌名 / 歌手 | **封面 / 不显示** |
| 暂停缩回 | `defaultNotchCollapsesWhenPaused` | 开 | **关** |
| 展开:显示歌词校准 | `defaultNotchExpandedShowsLyricsOffset` | 关 | **开** |
| 展开:歌名 / 歌手 / 专辑 | `defaultNotchExpandedShows{TrackTitle,Artist,Album}` | 全关 | **全开** |
| 歌词行封面 | `defaultNotchLyricRowShowsArtwork` | 开 | **关** |
| 歌词对齐 | `defaultNotchLyricsAlignment` | leading | **automatic(自动)** |
| 宽度(稳态) | `defaultNotchContentWidth` | 360 | **252** |
| 宽度(展开) | 新增 `defaultNotchExpandedContentWidth` | (共用稳态那份,360) | **482** |

没动的:风格(跟随封面)、屏幕、显示歌词、音浪与它贴哪只耳、展开的下一句预览 / 播放控制 / 快捷操作、
展开封面、歌词行封面位置、副行(下一句)、卡拉OK效果、两个自动隐藏 —— 用户的现值本来就等于默认。

- **改的是"这个键没存过时用什么"**:动过某一项的人键早已落盘、升级后那一项一字不变;跟着变的是新装
  用户和存量里从没动过那一项的人。这是刻意的,否则"定为默认"对老配置等于没发生。
- **两条原来写在代码里的理由被这次推翻了**,都改成了记录、没有删掉原文:
  - 对齐方式加「自动」那天(同一天早些时候)刻意没动默认,理由是"老用户升级不该看见对唱歌突然左右
    换边";现在默认就是自动。缓和的地方在于 `.automatic` 没有对唱信息时退化成 leading,非对唱歌观感不变。
  - 稳态宽 / 展开宽原本**共用一个常量**,理由是"新装机器上 hover 不会莫名多长一截";现在是 252 / 482
    一对,hover 会长。展开比稳态宽本来就是这对设置存在的意义(`NotchWidthBounds` 只要求展开 ≥ 稳态)。
- **展开态默认高度会变高**:多出歌词校准 + 歌名 + 歌手 + 专辑四行。展开态本来就是"hover 之后看详细
  信息"的那一面,这是知情接受的连带结果。
- **稳态那 252 是他存的设定值,不是最终宽度**:实际稳态宽 = `max(设定值, 耳朵下限)`,而下限跟左右耳
  配了什么走(见「宽度」节那张下界表)。新的默认耳朵组合(封面 / 不显示)的耳宽跟表里「封面 / 任一
  文字」那一档相同(表上记的是 **256**,`max(22+6, 15+5+6)` 那一支),已经高于 252 —— 所以默认配置下
  这台机器上卡片实际落在下界而不是 252。下界是每台机器的刘海宽算出来的,默认常量不去追它,`max` 兜着。
- **决策 #30(没有曲目时纯黑卡 + 左耳 App 图标)的前提从此是默认**:那一条写的是"他的机器关着暂停
  缩回,所以没有曲目时卡片按稳态尺寸挂着";`defaultNotchCollapsesWhenPaused` 改成关之后,新装用户
  一开始就是这个场景。
- **总开关 `notchOverlayEnabled` 没动**(仍默认关):它是引导向导第三步明确问过用户的三选之一,
  默认打开等于替新用户答了那道题。跟菜单栏那次的取舍一致。
- ⚠️ selftest 侧:新增的 `defaultNotchExpandedContentWidth` 补进了「重置覆盖闸」的豁免名单(理由同
  `defaultNotchContentWidth`:宽度是结构性设置,不进重置)。其余九项都在重置范围内,那条闸原样通过。


## 与其它功能的交互

- **设置搜索**(14 章 §1,2026-09-09):搜索命中本面「全部设置」抽屉里的行时,抽屉自动展开、那一行高亮并滚进视野(`NotchAllSettingsDrawer.expandForSearchIfNeeded`,SettingsView.swift;信号来自 Environment `settingsSearchPendingDrawer`);「风格」「屏幕」「左耳」「右耳」这几组的内容不是 `SettingsRow`,按组头登记、命中时亮的是组标题。新加一行设置要到 Core `SettingsSearchCatalog` 登记,否则 selftest `settings-search` 组会红。
- **PlaybackCoordinator(数据源)**:歌名、当前行/下一句、逐字时间轴、播放锚点、暂停冻结位置/时长、封面(系统 + 高清替代双份)、`notchAccentColor`、`isPlayingSmoothed`、歌词偏移。灵动岛不自己取任何数据。

### 几个具体决定

- **刘海画在卡片之上,不是之下**。物理刘海是屏幕上真实不发光的一块,任何窗口的像素都到不了那里;而卡片
  背景本来就铺满整张卡(只有顶行的**内容**给刘海让了空当)。画在下面的话,「磨砂玻璃」风格会把刘海那块
  渲染成半透明磨砂,而真机上那里恒为纯黑。形状复用卡片自己那个 `NotchHangingShape`(圆角 8,比卡片的 20 收得紧);
  `notchWidth == 0`(外接屏)时**什么都不画**——那种屏上就是一块贴着菜单栏顶边的胶囊,画个刘海是撒谎。
- **仿菜单栏两侧那几个图标会被宽卡片盖住,这是对的**。真机上就是这样,而且它恰好把"这个宽度会吃掉多少
  菜单栏"变成看得见的东西——是选宽度时的决策依据,不是渲染出错。
- **卡片内部一律不接事件**(`.allowsHitTesting(false)`)。改造前它天然点不动(预览在页顶钉条里,那一层
  收不到点击);挪进内容区之后真视图里那一整套控件突然全都可达了:三个播放键、**可拖的**迷你进度条、
  以及歌词行尾端那枚**封面缩略图**——最后这个打的是 `AppActions.shared.openLyricsWindow`,会
  `NSApp.activate` + 开一扇歌词窗口**直接盖在用户正在调的设置窗口上**。在一块用来"看样子"的画布上误点
  一下就改播放进度、或者凭空弹出一扇窗,不是想要的行为;本仓对预览的既定口径本来就是**不产生任何副作用**
  (`NotchPreviewChrome.setExpanded` 和 `OverlayPreviewChrome.controlsDidBecomeVisible` 两处空实现)。
  hover 展开不受影响:`.onContinuousHover` 挂在外层定高容器上(不在被禁用的子树里),并且紧挨着显式加了
  一句 `.contentShape(Rectangle())` 把整格钉成命中形状——既保证 hover 收得到,也把落在卡片上的点击吞掉。
- **舞台的裁切形状是顶直角、底圆角**(跟卡片同一个 `NotchHangingShape`),不是悬浮歌词那边的四角全圆。
  语义上它画的是屏幕上沿、而上沿是直的;几何上更是硬要求——卡片在舞台里**顶对齐**、顶角是直角,舞台
  如果顶上带 12pt 圆角,只要每侧余量小于 12pt 卡片那两个顶部直角就会被削圆,而"1:1 还原它贴在屏幕上沿
  的样子"正是这块画布的卖点。
- **~~没有两端渐隐~~ —— 这条 2026-09-06 已失效,但不是按预告补渐隐带,而是改成了缩放**(宽度上限 500 → 800 之后超宽成了可达的常态;渐隐带当天补过一版,用户否掉「预览放不下」,改成整组等比缩小,见「宽度 → 展开态可以更宽」末条)。原论证如下。⚠️ 但**余量是 0,不是想当然的三十几个 pt** ——
  别照抄"760 − 侧边栏 190 − 40 ≈ 530"这个算法:侧边栏是**可拖的**
  (`.navigationSplitViewColumnWidth(min: 170, ideal: 190, max: 220)`),窗口也真能拖到 `minWidth` 760
  (`SettingsWindowConfigurator` 往 styleMask 里插了 `.resizable`)。两样都推到极限时舞台只有约 499pt,

### 顺带修掉的五处

1. **两处裸调 `.shared`**。改造前 `notchOverlayCard` 里的 `applyContentWidthSetting()` 和 `applyScreenSetting()`
   都没有 `if settings.notchOverlayEnabled` 守卫,违反本章设计决策第 1 条——灵动岛关着的用户只要碰一下宽度
   滑杆或改一下屏幕,就会把整扇窗(NSPanel + NSHostingView + 一串 Combine 订阅和通知观察者)建出来。
   菜单栏快捷面板里的同一根滑杆本来就带着这条守卫,设置页这两处是最后没带的。

   ⚠️ **补守卫必须连带补一次"打开时重新应用几何",否则是拆东墙补西墙**(审查抓到的,见设计决策第 15 条):
   `setVisible(_:)` 原来只应用两个隐藏偏好 + `orderFrontRegardless`,**从不重算几何**。于是"关掉 → 关着
   改宽度/换屏 → 再打开"这条完全正常的序列会让窗口按**旧宽度**、甚至**旧那块屏**冒出来。而且前提比想象中
   容易满足:**关掉这个动作本身就走 `.shared.setVisible(false)`**,`.shared` 一定已经建出来了。现在
   `setVisible(_:)` 的 visible 分支里补了一句 `recomputeGeometry(animate: false)`(内部四个 `@Published`
   和 `setFrame` 全部判等再写,几何没变时是纯读)。**悬浮歌词那边是同款结构、同样漏宽度**,一并补了
   `setWidth(持久化值)`(见 04 章第十四步)。
2. **`NotchPreviewChrome.refreshGeometry()` 里的两个判等去掉了**。判等省下的那次 `objectWillChange`
   没有任何收益(这个方法只在屏幕插拔和「屏幕」浮层提交时跑),却掐掉了工具栏「屏幕」摘要唯一的刷新通道——
   那截摘要是从 `NSScreen.screens` 现算的**纯派生值**,而那个全局没有任何 publisher。判等版本会在"刘海几何
   恰好没变"的插拔里让按钮停在旧值:典型场景是一台没有内建刘海的机器接两块菜单栏等高的外接屏,钉住的那块
   拔掉/插回,`notchWidth` 恒 0、`notchHeight` 相等,于是按钮上仍写着已经拔掉的那台显示器的名字。
3. **换屏之后预览的刘海几何不刷新**。`NotchPreviewChrome.refreshGeometry()` 原来只订了
   `didChangeScreenParametersNotification`,用户在设置里把灵动岛从内建屏换到一块没有刘海的外接屏时不重算。
   改造前这只表现为让位宽度/高度略有出入;编辑台把刘海本身画出来之后,它会直接表现成"画了一块那块屏根本
   没有的刘海"。现在选完屏也调一次。
4. **宽度读数在拖动中冻住**(这条在**悬浮歌词**编辑台里,一并修了)。`widthValueText` 读的是裸的
   `settings.overlayWidth`,而落盘推迟到松手之后、窗口宽度走的却是 `draggingWidth ?? settings.overlayWidth` ——
   于是拖动全程读数停在上一次提交的数字上不动,窗口就在旁边跟着变宽。是 04 章第六步加 `draggingWidth`
   那次漏掉的一处。灵动岛这根从一开始就读 `baseWidth`。
5. **两处陈旧注释/文档**(同样在悬浮歌词那边):`widthBinding` 的文档还写着"落盘是**实时**的,不再有
   '松手才写'那一层",而加 `draggingWidth` 之后早就改成延迟提交了;04 章第六步同一段、以及规格表里
   「窗口宽度 420~1000pt」(区间早就扩到 300~1400)也一并订正。

### 收尾三项(2026-08-31,用户逐条拍板)

1. **宽度读数改报「带耳朵的真实宽度」**(用户原话:「这里的宽度帮我改为带上耳朵的宽度,这样就没有歧义了」)。
   见「宽度」节。两个入口都改,菜单栏快捷面板那根为此给 `sliderRow` 加了个可选的 `displayValue`
   闭包(不给的另外两根滑杆行为一字未变)。
2. **灵动岛前景取色并进「风格」的「跟随封面」**(用户拍板:开关跟悬浮歌词分开,但**合并到现有「跟随封面」
   的语义上,灵动岛不多加一个开关**)。见「风格」「强调色」两节。落点只有一处:`NotchPlayback` 那条
   `CombineLatest` 的第二个输入从 `s.$followsCoverArt` 换成 `s.$notchCardStyle`。**没有新增设置项、
   没有新增 UserDefaults 键、没有迁移代码** —— 新语义是从既有设置**推导**出来的。
   ⚠️ 但它是**行为变更**,两种既有配置的观感会变(默认配置不变:默认风格就是「跟随封面」、
   `followsCoverArt` 默认也是开):
   - 风格=纯黑/磨砂玻璃/深色渐变 且 `followsCoverArt` 开着 → 前景从封面色变**白**;
   - 风格=跟随封面 且 `followsCoverArt` 关着 → 前景从白变**封面色**。
   没做"一次性迁移快照"是刻意的:那要么得新增一个存储键(用户明确不要多加开关),要么得把推导变成
   一次性写死,反而留下一个说不清语义的历史值。

- **从卡片上点开的浮层开着时预览钉在展开态**(`keepsExpandedForPopover`:`popover != nil` 且 `popoverAnchor` 是 `.hotspot`;不分哪个浮层):从卡片上点开浮层时卡片本来就是展开的,浮层一开它缩回去就是"选中的东西自己变形了"。**从工具栏点开的不钉、两头都不碰**(第四轮用户:「点开这些选项,不要把下面的自动展开呀」)—— 那条路卡片本来是稳态,凭空展开是多余的动作,想看展开区把指针移到卡片上即可。落点反复过三次:第二轮只钉「展开态」那个浮层(不分从哪开),第三轮扩成任一浮层(含工具栏),第四轮收回到"只有卡片上点开的"。浮层一关就放开,指针若还在卡片上下一次 hover 事件会再展开。
- 没做的:点卡片**背景**打开「风格」。区域几乎铺满整张卡,剩下能点到"背景"的只有刘海空当,做了也点不到;要它的话应该给「风格」另找一个显眼的入口,不是靶子藏在缝里。

## 设计决策与已知坑

1. **`.shared` 不变量(最重要)**:`NotchLyricsWindowController.shared` 是 `static let`,任何代码只要引用一下(哪怕读个属性)就会执行 init 建窗口并立刻 orderFront——灵动岛关着的用户会凭空多出一个胶囊,且它 level 在菜单栏之上会盖住菜单栏图标。所有外部路由(AppDelegate/SettingsView/MenuBarMenu/NotchMirrorManager/预览)都必须只在灵动岛确实启用或用户主动操作的分支里碰 `.shared`;预览为此专门有不碰实例的 static 几何函数和替身 chrome。
2. **convenience init 参数不能给默认值**:`pinnedScreenID` 给了默认值后 `NotchLyricsWindowController()` 会解析到 NSWindowController 继承来的 `init()`,建出没有窗口的空壳,灵动岛静默消失且无任何报错(2026-08-16 实翻三次构建)。主实例也显式传 nil。
3. **窗口 level 必须 `.screenSaver` + 覆盖 `constrainFrameRect` 原样返回**:`.statusBar` 都不够(被菜单栏专属渲染层盖住,截图能看到但肉眼看不到);AppKit 默认会把 frame 夹回 visibleFrame 以内导致胶囊脱离刘海。做法对照 DynamicNotchKit 等真实开源实现。
4. **窗口透明区绝不能加 background/contentShape**:透明区压着系统菜单栏,纯透明点击可穿透,加一层哪怕全透明的 contentShape 点击就被吞掉——用户点不动被盖住的菜单栏(2026-08-16 探针窗口实测)。这是"窗口常驻最大尺寸"重构唯一的真风险点。
5. **`.scaledToFill()` 之后、`.clipShape` 之前必须显式钉 frame**:fill 会协商出比可见区更大的 frame,clipShape 按紧邻上层 View 的 frame 画圆角,不钉的话圆角落在偏大矩形边缘、可见区仍是直角——像素级采样踩了三版才找对根因("肉眼看着圆"是模糊的柔化骗人)。背景大图和封面小图两处都适用。
6. **投影与窗口余量是绑死的一对**:展开态卡片加 `.shadow` 必须同时给窗口留投影半径的余量,否则阴影被窗口矩形硬裁、底部圆角外留两块直角残影;2026-08-17 投影和余量已一起撤掉(投影观感是"卡片外糊一层灰",拆穿"从刘海长出来"的设计语言),要加回来必须两件一起。
7. **Combine sink 必须用参数值**:`@Published` 在 willSet 时机发布,闭包里回头读存储属性拿到的是旧值——本功能相关代码(isPlayingObserver、NotchMirrorManager、VolumeMonitor)处处遵守,项目已实测踩过多次。
8. **`isCollapsed` 必须是计算属性**:公式只有一份但挂在 hover 不会走的赋值路径上,导致"暂停时 hover 没反应"(isExpanded 变了 isCollapsed 没跟上);2026-08-17 改计算属性后两个输入哪个变都即时生效。
9. **`hasShadow = false` 是刻意的**:AppKit 给无边框透明窗口自动算的阴影会在贴死屏幕顶边的窗口里内嵌出一圈淡灰,破坏"与屏幕边缘融为一体"。
10. **歌词行的"硬切"和"真遮挡"是两个不同的问题,别拿一个的修法去解释另一个**(2026-08-22):稳态下 HStack 的两个兄弟**永不重叠**,clip 边界恒在封面左边 10pt —— 这一条经真机连拍 60 帧逐像素核过(封面左侧那条 spacing 带里 0 个文字像素)。用户报的「被封面挡住」主要是那个**硬切口紧贴封面**的观感,修法是渐隐带。真正的像素级重叠只发生在"封面在场性变化 + 活动动画同一次更新"这个窄窗口里,修法是 `.animation(nil, value:)`。两者独立,缺一个另一个都还在。
11. **单行面的「唱完就切」不能照搬歌词窗口那套**(2026-08-23):见「唱完就切到下一句」。多行列表间奏里有「•••」可停靠,单行面没有 —— 同一份 `scrollLeadIndex` 搬过来的话,长间奏里屏幕上就一直挂着一句**已经唱完的**歌词,而且没有任何视觉线索说明它唱完了。
12. **模糊半径不能照搬**:歌词窗口的 60pt 模糊在灵动岛的矮宽画布上会把所有封面抹成同一块深灰,"跟随封面"失去意义;20 是实测保留主色调差异的取值。
13. **设置页编辑台的高度必须是常量**(2026-08-31):它挂在**可滚动内容区**里,高度一变下面所有卡片跟着跳一下,而 hover 展开恰好让卡片长高 76pt。做法是舞台按**展开态**留一格(`cardAreaHeight = contentTopInset + 44 + 76`),卡片在这一格里顶对齐地变高变矮,外层一动不动。这条跟悬浮歌词编辑台那条"高度不许依赖 `overlayWidth`"是同一条纪律的两个形态:那边怕宽度带动高度,这边怕 hover 带动高度。⚠️ `contentTopInset` 本身会随屏幕变,那是插拔显示器才会发生的事,不在交互路径上。
14. **打开某个悬浮窗时必须把"已配置好的偏好"一并应用,几何也算偏好**(2026-08-31):`setVisible(_:)` 历史上只应用"隐藏"类偏好(`hideDuringScreenCapture` / `hideWhenNotPlaying`,悬浮歌词那边 2026-08-30 又补了 `lockPosition`),**宽度和屏幕一直漏在外面**。这在"设置项都带 `if 开关 { .shared.… }` 守卫"的前提下就是个真 bug:关着改的值没人应用,而**关掉这个动作本身就已经把 `.shared` 建出来了**,所以"关 → 改 → 开"必中,窗口按旧宽度/旧那块屏冒出来。恢复源只剩屏幕插拔通知和"下一次开着时再改一遍"(`isPlayingObserver` 自 2026-08-17 起也不再重算几何)。⚠️ 以后再往这两个控制器加"设置页改完要显式调一下才生效"的项(几何、层级、材质…),**同时**要问一句"关着改完再打开,谁来应用它"。
15. **`NotchHangingShape` 只能 `.stroke` 不能 `.strokeBorder`**(2026-08-31):`strokeBorder` 是 `InsettableShape` 的方法,而这个形状是手写的普通 `Shape`(顶直角底圆角,`UnevenRoundedRectangle` 要 macOS 26 才有)。编辑台那圈拖宽度时的虚线轮廓因此**骑在**卡片边界上、各半个像素在内外,1pt 虚线看不出区别——不值得为此给这个共用形状加一层 inset 实现。
16. **音浪包络:字内稳态不能动,只能在起音和换气上做文章**(2026-09-02)。08-23 试过按已唱比例连续插值,每一跳更平均、反而更不像人声——因为它改的是字内稳态。这次的起音脉冲(1 + 0.25,80ms 衰回)与换气泄放(1 → 0.6,250ms)都不碰稳态,所以能叠在 09-01 调好的双正弦手感上。配套的「乘完再夹」是必要条件:以前 `min(1, amplitude)` 在乘曲线之前,任何 >1 的振幅都被吃掉,包络里的瞬态根本到不了屏幕。数学在 `VocalEnvelope`(Core、selftest 14 条),`NotchLyricsView.vocalAmplitude` 只剩读快照与算位置——XxxxView 里不放数学。求值频率刻意不提:80ms 攻击 = 80ms 采样,再快就撞 08-19 的性能红线。
17. **「暂停/无播放时隐藏」先播收起动画再 orderOut(2026-09-02,推翻此前"设置语义"的判断)**:原来 `updateActualVisibility` 在平滑播放态翻成暂停的同一个回调里就 orderOut,0.45s 的收起弹簧一帧都播不出来,文档写成"想看收起动画就把隐藏关掉"。改成:应隐藏时先留窗,`NotchWindowRoot.collapseSettleDelay`(0.25s;首版 0.5s,用户目验"半秒太久"砍半,同时 `stopGracePeriod` 0.5→0.25,暂停到消失总时长 ≈1s→≈0.5s;弹簧本身不动,隐藏关着时仍要收完整)后到点重算——`hideGeneration` 代数未被作废、`isVisible` 与开关仍开、`PlaybackCoordinator.isPlayingSmoothed` 仍为假——三样都成立才 orderOut;任何一次求值出"要显示"都 `cancelPendingHide()`(代数加一 + 取消 DispatchWorkItem),挂着期间 `lastAppliedShouldShow` 保持 true(窗口确实还在)。**不重排**:同样结论再进来(设置同步等路径)不刷新计时,否则隐藏会被一推再推。三种情况维持立刻隐藏:`collapsesWhenPaused` 关着(没有收起动画可播)、`NSWorkspace.accessibilityDisplayShouldReduceMotion`(卡片本来就是跳变)、`isVisible=false`(用户手动关灵动岛);首次求值(`lastAppliedShouldShow == nil`)也直接 orderOut。两处澄清:①"暂停 0.3s 又播放会闪"本来就不成立——喂进来的是平滑态,停止自带 0.5s 宽限(`stopGracePeriod`),这次真正消掉的是"暂停 0.5～1s 又播放"那一窄段的闪隐闪现;②截屏/录屏隐藏走的是 `sharingType = .none`、锁屏不经此函数,所以不存在"安全性隐藏被延迟"的问题,不必拆两条路径。副本销毁(`teardown`)先作废挂着的隐藏。已知取舍:计时器到点时若鼠标正悬在卡片上,窗口仍会在指针下消失(与改前一致),"悬停期间不隐藏"需要再接一条触发,未做。
    **同日第二版(用户目验后)**:先收起再消失被否——"动画效果不是很好,直接从正常大小缩小到无,不要经历那个暂停状态"。改法:① `isCollapsed` 加 `hideWhenNotPlaying` 维度,开关开着时暂停**不**触发收起(广告插播仍收起,广告期间不隐藏);② 新增 `isVanished`,`NotchWindowRoot` 对整卡 `.scaleEffect(0.001, anchor: .top)` + `.opacity(0)`,`vanishAnimation` = 退场 `easeIn(vanishDuration 0.2s)` / 回场 `spring(0.42, 0.8)`;③ 控制器:应隐藏 → `isVanished = true` → `vanishSettleDelay`(0.25s)后三重校验 → orderOut,**隐藏期间保持 true**(下次露面从刘海里长出来,不会先满幅一帧);恢复 → 先 orderFront 再 `isVanished = false`(反了会在看不见的窗口里播完);立刻隐藏分支与"到点却该显示"的兜底都把它翻回 false,别让一张缩成一点的卡留在可见窗口里。`collapsesWhenPaused` 不再是这条路的前置条件(没有收起动画可播的问题不存在了)。常量 `collapseSettleDelay` 已删,改为 `vanishDuration`/`vanishSettleDelay`。

21. **展开态加宽:两个键、一条不变量、一处落盘(2026-09-06,用户提出)**。用户要的是"宽度区间":下限 = 稳态、上限 = 展开。三个取舍:①存**绝对值**不存"加宽多少"的差值 —— 用户的心智是上下限两个数,编辑台读数也是两个绝对宽;差值模型会让调稳态时展开跟着漂。②不变量只有「展开 ≥ 稳态」,读侧 `max`、写侧 `normalized`,都在 `NotchWidthBounds` 一处,三个写入口共用 `commitWidths` —— 之前"宽度"三处各自写 `settings.notchContentWidth = …` + 守卫 + `applyContentWidthSetting()`,再加一个键就是六份,趁这次收成一处。③编辑台用自绘双滑块而不是两根单滑块:两只滑块不越过对方(停下、不推走 —— 推走会顺手改掉用户早就调好的稳态),重叠时按位移方向认领;拖上限时把预览置成展开态,否则改的东西在画布上看不见。默认两宽相等,老用户升级后 hover 观感逐字不变。窗口常驻展开宽,多出来的两截透明区跟下方一样点击穿透。区间上限同日从 500 抬到 800(用户:「最宽还是有点小了」),舞台放不下时整组等比缩小(见 #22)。

26. **展开 / 收回是「原地淡出、在新位置淡入」,不是平移;隐式 `.animation(_:value:)` 不许出现在会随卡片一起动的子树里(2026-09-06,用户报两件事:「展开的时候音浪会有抖动,在原始的位置和即将出现的位置之间闪动」「歌词这些都是平移过去的,它并不是一个重新出现的过程」)**。两件事逐帧抓窗(SCK 探针 + 每帧 PNG)分别坐实:
    - **音浪**:播放态展开时 5 根条子散开、几根不见,暂停态(TimelineView 停表)则完好;把 `EqualizerBars` 里的 `.animation(.linear(0.04), value: 高度)` 从 HStack 挪到每枚 Capsule 上**无效**,整个拿掉后全程紧凑。机制:卡片尺寸弹簧正把这排条子平移,而每次 tick 让 `.animation(value:)` 的 value 变一次,SwiftUI 就用那条 linear 重新接管作用域里正在动的属性 —— 条子位置在内,各按各的 tick 相位在"弹簧中途"和"目标位置"之间跳。修法:补间只能靠采样密度 —— interval 改到 30Hz(与逐字填色同一个表),直接取连续曲线的值,不再有任何隐式补间。**规则**:凡是会随卡片尺寸弹簧一起动的子树,里面不准放会随时间反复触发的 `.animation(_:value:)`;一次性的(如 value 是 isExpanded)可以。
    - **歌词行 / 头部 / 展开区**:此前都是 VStack 里吃满卡片宽的行,卡片从稳态宽长到展开宽时靠左的文字跟着左沿滑一百多 pt、头部插入时歌词行还同时下滑。改成 `cardBodyLayer`(§歌词行):每块常驻、定宽、定 y、以卡片中心为锚,只切透明度。**为什么不是 if/else 换视图**:同日试了三版(if/else 直接放 VStack;放进定宽 overlay 容器;只挪歌词行),正在过渡的那份或新插进来的那份都跟着卡片左沿滑 —— SwiftUI 对进出场视图怎么摆跟持久视图不是一套规则,而且不透明;**持久**视图被居中这件事已被刘海胶囊逐帧验证。**两个撞过的坑**:① 比卡片宽的定宽块**不能做 ZStack 的子视图**(ZStack 会被撑到展开宽,GeometryReader 把内容摆在左上角,整卡内容右移 (展开宽 − 稳态宽) / 2)—— 要做 overlay;② overlay 里的几块要包进**显式**的 `ZStack(alignment: .top)`,不能让 @ViewBuilder 吐的 TupleView 直接套 `.opacity`:套了修饰符的 TupleView 是一个视图,内部按居中叠,稳态下最高的展开区把整体撑到 220pt、居中后歌词行被顶出卡片裁没了。**代价**:两份歌词行与展开区常驻,藏着的那份必须停表(`notchCardLayerActive` → 逐字填色与迷你进度条的 TimelineView 都按它 paused),否则 30Hz 热路径翻倍;藏着的一律不吃点击(行里有封面按钮、播放键、校准键)。**观感**:展开时稳态歌词在原位淡出,展开态的头部 / 歌词 / 预览在各自最终位置淡入、被长大的卡片边沿逐渐"露出来";收回反之。顶行两只耳朵**仍随边沿平移**(封面贴左、音浪贴右,那是岛本身在变形,用户没有异议)。复测:展开 16 帧 / 收回 24 帧全 60fps,稳态歌词行 x 一像素不动,音浪 5 根紧凑、右边距恒定。
